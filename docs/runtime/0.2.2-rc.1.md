# DSH 0.2.2-rc.1 运行时勘察记录

> **适用版本：DSH 桌面版 0.2.2-rc.1。** 来源：`app.asar` 与 npm 上 `@deepseek-ai/*` 包的原文、`0.2.1-rc.5` 与 `0.2.2-rc.1` 两版逐包对比、以及本机实测。
>
> 这份文件只记录**某个 DSH 版本上观察到的事实**，会随 DSH 升级失效。上一版见 [0.2.1-rc.5.md](0.2.1-rc.5.md)；稳定的工程约定写在 [../plugin-conventions.md](../plugin-conventions.md)。

## 0. 一句话结论

0.2.1-rc.5 → 0.2.2-rc.1 对插件是**非破坏性升级**：探针 16 项全 PASS，会话日志格式仍是 v4，持久化 seam 仍然没有删除 API`session-delete` 的端到端冒烟 24/24 通过。**没有需要改代码的宿主变化。**

实测基线：`dsh --version`、`Info.plist`、`app.asar` 内 `/dsh/package.json` 三处都是 `0.2.2-rc.1`。

## 3. 版本闸门：预发布语义（**更正上一版的结论**）

`@deepseek-ai/dsh-app-boot` 里判定插件版本要求的函数，两版**实现完全相同**：

```js
function satisfies(runtimeVersion, range) {
  return (
    range.trim() !== "" && semver.satisfies(runtimeVersion, range, { includePrerelease: true })
  );
}
```

`includePrerelease: true` 意味着预发布版本参与常规范围比较。用宿主自带的 semver 7.8.6 实测（✓ = 满足）：

| range                   | 0.2.1-rc.5 | 0.2.1-rc.6 | 0.2.1 | 0.2.2-rc.1 | 0.2.2 | 0.2.3-rc.1 | 0.3.0-rc.1 |
| ----------------------- | :--------: | :--------: | :---: | :--------: | :---: | :--------: | :--------: |
| `>=0.2.1-rc.5 <0.3.0`   |     ✓      |     ✓      |   ✓   |     ✓      |   ✓   |     ✓      |     ✓      |
| `>=0.2.1-rc.5 <0.3.0-0` |     ✓      |     ✓      |   ✓   |     ✓      |   ✓   |     ✓      |     ✗      |
| `^0.2.1-rc.5`           |     ✓      |     ✓      |   ✓   |     ✓      |   ✓   |     ✓      |     ✗      |

**结论更正**：[0.2.1-rc.5.md](0.2.1-rc.5.md) §6.7 与 [ADR 0005](../adr/0005-dsh-version-compatibility.md) 里的表是拿**不传 options 的 `semver.satisfies`** 算的，和宿主真正的判定不一致，因此「任何新 patch tuple 的预发布都不满足现有多数 range」这个说法**不成立**：`>=0.2.1-rc.5 <0.3.0` 接受 0.2.2-rc.1。

两个仍然成立的细节：

- 想**排除**下一个 minor 的预发布，上界要写 `<0.3.0-0`；`^0.2.1-rc.5` 会自动带上这个 `-0` 上界。
- 声明 `engines.dsh` 依然是「承诺」而非「白送」：range 内的任何版本都会被放行，包括没验证过的。是否声明仍按 ADR 0005 的验收节奏决定。

### 启动期拒绝的形态（本版读到的事实）

- 拒绝发生在 **composition 边界**：被拒的插件行在启动器自己的 composition 里变成 `disabled: true` 的游离行，**不会 import 它的模块**；被拒的 bundle 直接跳过，并列入 `skippedBundles`。
- 豁免写在 profile 自己的 `compatibility.json`（不是 `package.json`），键是精确的 `包名@版本` → 精确的 DSH 运行时版本列表。
- **插件升级或 DSH 升级都不会继承豁免**（原文："neither a plugin upgrade nor a DSH upgrade inherits permission"）。所以升级完要重新确认。
- 没有 `compatibility.json` 就等于没有豁免。本机 desktop profile 目前没有这个文件，也没有插件被拒。

## 4. 会话日志格式

- 常量在 `@deepseek-ai/dsh-session`：`SESSION_FORMAT_VERSION = 4`，两版相同。
- 文件名由 JSONL 后端的 `generationLogFilename(version, compression)` 生成，磁盘上仍是 `session.v4.jsonl.zstd`；`locate(meta)` 仍返回 `{ kind: "jsonl", path }`。
- 因此「按目录删除」的策略继续有效，插件不需要知道格式版本；继续**不要写死文件名**。

## 7. 这次踩到的坑

1. **asar 数据区有 4 字节对齐填充**。文件数据的起点是 `16 + align4(jsonLength)`，不是 `16 + jsonLength`。本版 `jsonLength = 5748746`，真实起点 `5748764`——少算这 2 字节会让每次读文件整体偏移：`package.json` 解析失败（版本号变 `?`），而以「搜特征」为主的检查恰好还能命中，于是**探针一边报错一边显示全绿**。仓库的 [probe-runtime.mjs](../../scripts/probe-runtime.mjs) 已修。
2. **别用裸 `semver.satisfies` 推算闸门**。宿主传了 `includePrerelease: true`，两者对预发布的结论可能相反（见 §3）。
3. 上一版记录的坑仍然有效：client 半要刷新页面、仓库外直接 `import('@deepseek-ai/dsh-*')` 会 `ERR_MODULE_NOT_FOUND`、`link:` 安装无法激活、Typert Remote 方法必须声明在导出类自身原型上、headless 组合没有 `workspaceRegistry`。

## 8. 下次升级要做什么

1. 升级前先跑一次 `pnpm probe:runtime` 留基线，升级后立刻再跑一次，对比差异。
2. 新建 `docs/runtime/<新版本>.md`，按本文件的表逐项核对，**不要覆盖**旧版本记录。
3. 重点看三件事：`SESSION_FORMAT_VERSION`、`sessionPersistence` 是否终于有了删除 API、`satisfies` 的 options 有没有变。
4. 跑 `pnpm smoke:session-delete`（临时 `DSH_HOME`，不碰共用 profile），再在桌面版里确认插件状态条不是只读模式。
