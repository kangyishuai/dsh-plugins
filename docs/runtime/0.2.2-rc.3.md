## 2. 探针：先 71 PASS + 1 FAIL，修完 72/72

`pnpm probe:runtime` 第一次在 rc.3 上跑：**71 PASS + 1 FAIL**。唯一 FAIL 是：

```
FAIL  seam Modal 的 [data-modal-autofocus] 焦点约定（确认按钮默认选中）
      :: 文件不存在：@deepseek-ai/dsh-web-frontend/dist/assets/index-ghOpC9uV.js
```

**根因是探针写死了带内容哈希的产物名，不是宿主删了能力：**

- rc.3 的 `dsh-web-frontend/dist/assets/` 里只有 `index-Ciz7DZxv.js`（1,093,870 字节）与 `index-CSAdOBx6.css`（92,252 字节），rc.2 的 `index-ghOpC9uV.js` 已经不在了。文件名就是构建哈希，**每个版本都会变**。
- 能力本身还在：`index-Ciz7DZxv.js` 里 `data-modal-autofocus` 出现 **2 次**，Modal 打开时仍然是 `l.querySelector("[data-modal-autofocus]") ?? l.querySelector(b7) ?? l` 再聚焦。

**修法**（只改 `scripts/probe-runtime.mjs`，不动插件）：给私有 seam 检查加 `filePattern`——对 asar 全路径做正则，扫到哪个算哪个；这条从 `file` 换成
`filePattern: /^\/dsh\/node_modules\/@deepseek-ai\/dsh-web-frontend\/dist\/assets\/index-.*\.js$/u`。顺手把四段一模一样的 seam 循环并成 `runSeamChecks()`。修完 **72/72 PASS**。

这正是 [AGENTS.md](../../AGENTS.md) 硬性约定 1 的现场案例：**不写死 DSH 内部实现**，带哈希的路径只能「扫描 + 匹配已知模式」。以后遇到 `dist/assets/*` 一律用 `filePattern`。

## 4. 会话日志与持久化

- `SESSION_FORMAT_VERSION` 仍是 `4`；磁盘文件名仍由后端生成（`session.v4.jsonl.zstd`）。继续**不要写死文件名**，用扫描 + `locate()`。
- `sessionPersistence` 仍然没有删除 API，session-delete 继续自己搬目录。

- **【实测】`session/event` 的顺序：`turn/start` 先于 `user/message`。** 一轮完整链路是
  `turn/start → agent/inbox/spliced → step/start → user/message → … → turn/end`。
  插件若在 `turn/start` 里清理「等这条用户消息回来再归因」的状态，那状态永远等不到消息
  （next-step v0.4 的 followup 就踩了这个坑，只在 `user/message` 收尾才对）。
- **【实测】`user/message` 的形状是 `{ data: { content, source: { kind }, role, id } }`。**
  文本块在 `data.content`（不是 `data.message.content`，后者是 `assistant/message` 的形状）；
  `data.source.kind` 区分来源（用户手打是 `"user"`，插件的隐藏注入按自己的 kind 走）。
  要「只认用户自己打的字」，两个条件都要判。

## 7. 一次瞬时失败：next-step web 冒烟首跑 2 FAIL、重跑 59/59

第一次跑 `pnpm smoke:next-step` 是 **13 PASS + 2 FAIL**（共 15 项，后面的断言因为拿不到卡片没有执行）：

```
FAIL 卡片在答后出现（conversation.chat.turnTail） :: 等 120s 后没有任何 section[data-next-step-card]
FAIL 日志里有卡片记录（可跨重启重建）              :: 期望>=1 实际=0
```

截图里能读到的现场：助手已经完整回答了「二分查找」三问（远超 `MIN_ANSWER_CHARS = 80` 的道闸），卡片位置是 **「生成下一步建议｜操作失败，请重试」**——即用户可见的兜底按钮出现、点了，但补生成调用**失败**。所以不是「回答太短被门挡」，也不像客户端没渲染。

**复跑结论**：带 `SMOKE_KEEP=1 SMOKE_DEBUG=1` 单独重跑一次，**59/59 PASS，0 SKIP / 0 FAIL**（会话日志里 `plugin:next-step/card`、`phase=sent`、胶囊 WYSIWYG 等 44 项都过了）。

**归因（2026-11-14 二次排查后更正）**：先前把这次失败写成「CPU 争抢下的瞬时失败」——**那个说法是错的**，照原样制造同样的并发负载（三个桌面回归 + 一次 web 冒烟同时跑）**没能重现**，59/59 通过。真正确定的是下面两件事：

1. **机制确定**：卡片生成走 `writeCardFor()`，用 `setTimeout(() => controller.abort(...), settings.timeoutMs)` 兜底，默认 `timeoutMs: 20000`。超时后 `generate()` 以抛错收场，`writeCardFor` 落到 `catch` 后返回 `{ok:false, reason:"aborted"}`，客户端把 `aborted` 映射成 `error.failed`「操作失败，请重试」——与截图里的文案一致。用 `timeoutMs: 150` + 一个挂起的假 `generate` 驱动真实 `writeCardFor`，得到 `{ok:false,reason:"aborted"}`、abort 的 reason 是 `next-step timeout`，**机制可确定性复现**。
2. **子原因不可恢复**：`failed / schema / aborted / not-needed` 四种原因**都映射到同一句** `error.failed`，光看界面分不出来；而中止路径当时**既不计数、也不写 `lastSkip`、更不落会话日志**（`catch` 里还有 `if (!controller.signal.aborted)` 把中止直接跳过），诊断面板显示「失败 0」。首跑没设 `SMOKE_KEEP`，临时 home（含内存态）已随进程销毁——所以**这次失败的确切子原因事后无法还原**，只能确认它不是「回答太短被门挡」（回答远超 80 字）。

**已据此改进（见本仓库下一版）**：next-step 增加 `counters.aborted` 与中止时的 `lastSkip`（超时写 `generation timeout after Ns`），失败文案改为 `error.aborted`「生成超时或被取消，请重试」；`smoke:next-step` 在没出卡时读面包屑 `data-next-step-retry-error` 把插件自报的原因打出来，并**在断言失败时自动保留临时 `DSH_HOME`**（不再只有 `SMOKE_KEEP=1` 才留现场）。下次同类失败可以直接读出是超时还是别的。

**不是 rc.3 的破坏性变化**：探针里 next-step 依赖的 seam（`turnTail` 槽、`sessionProjections.register`、`appendPluginRecord`、`llm.prepareCall` + `call.stream`、`use` 路由与 `agents.get(id).model.current()`）在 rc.3 上都还在，两次单独重跑（含一次并发负载下）都是 59/59。

排查建议：冒烟建议与桌面回归**串行**跑（都要打真实模型、都吃 CPU），但别再把它当成已证实的因果；再遇到同类失败，先看冒烟新打出的 `插件报错（没出卡时）` 与保留下来的临时 home 里宿主日志。

## 8. 下次升级要做什么

1. 升级前跑一次 `pnpm probe:runtime` 留基线，升级后立刻再跑；先分清「能力没了」和「源码形态变了导致匹配不到」。rc.2 是后者，rc.3 还是后者（哈希资源名）。
2. 探针里**任何带哈希的路径**都不要写死；`dist/assets/*` 用 `filePattern` 扫。
3. 新建 `docs/runtime/<新版本>.md`，更新 AGENTS.md、`plugin-conventions.md`、两份根 README 的徽章与各插件兼容表（`pnpm check:docs` 会拦）。
4. 重点看三件事：`SESSION_FORMAT_VERSION`、`sessionPersistence` 是否终于有删除 API、`satisfies` 的 options 有没有变；外加 client 半有没有再换构建形态。
5. 冒烟**串行**跑：先四条 web（临时 home），再四条桌面（live 版 + CDP 9222），不要并发。
