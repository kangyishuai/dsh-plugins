## 2. 探针：先 71 PASS + 1 FAIL，修完 72/72

`pnpm probe:runtime` 第一次在 rc.3 上跑：**71 PASS + 1 FAIL**。唯一 FAIL 是：

```
FAIL  seam Modal 的 [data-modal-autofocus] 焦点约定（确认按钮默认选中）
      :: 文件不存在：@deepseek-ai/dsh-web-frontend/dist/assets/index-ghOpC9uV.js
```

**根因是探针写死了带内容哈希的产物名，不是宿主删了能力：**

- rc.3 的 `dsh-web-frontend/dist/assets/` 里只有 `index-Ciz7DZxv.js`（1,093,870 字节）与 `index-CSAdOBx6.css`（92,252 字节），rc.2 的 `index-ghOpC9uV.js` 已经不在了。文件名就是构建哈希，**每个版本都会变**。
- 能力本身还在：`index-Ciz7DZxv.js` 里 `data-modal-autofocus` 出现 **2 次**，Modal 打开时仍然是 `l.querySelector("[data-modal-autofocus]") ?? l.querySelector(b7) ?? l` 再聚焦。

**修法**（只改 `scripts/probe-runtime.mjs`，不动插件）：给私有 seam 检查加 `filePattern`——对 asar 全路径做正则，扫到哪个算哪个；这条从 `file` 换成
`filePattern: /^\/dsh\/node_modules\/@deepseek-ai\/dsh-web-frontend\/dist\/assets\/index-.*\.js$/u`。顺手把四段一模一样的 seam 循环并成 `runSeamChecks()`。修完 **72/72 PASS**。

这正是 [AGENTS.md](../../AGENTS.md) 硬性约定 1 的现场案例：**不写死 DSH 内部实现**，带哈希的路径只能「扫描 + 匹配已知模式」。以后遇到 `dist/assets/*` 一律用 `filePattern`。

  文本块在 `data.content`（不是 `data.message.content`，后者是 `assistant/message` 的形状）；
  `data.source.kind` 区分来源（用户手打是 `"user"`，插件的隐藏注入按自己的 kind 走）。
  要「只认用户自己打的字」，两个条件都要判。

### 6.1 核对「页面到底加载了哪一版 client 半」（2026-11-14）

- **【实测】`window.__DSH_BOOT__.entries[].rev` 不是内容哈希。** 同一个 profile、同一个 `rev`
  （`7f2db5490a38`）下，宿主先后下发过至少三份内容不同的 `next-step/lib/client.js`：
  npm 0.4.0、本地修复版、npm 0.4.1。把它当构建哈希或"内容变了就换"的凭据会得出错误结论
  ——本次排查就差点把"修复没生效"判成结论。它只适合当缓存破坏参数。
- **【实测】要确认当前跑的是哪一版，只有两条可靠路径。** ① CDP：`Network.enable` → `Page.reload`
  → 抓 `dsh-app://app/plugins/??<pkg>/client.js&rev=...` 这条请求的 `Network.getResponseBody`，
  直接对源码做特征检查；② 读插件设置页里的诊断行构建哈希（由插件自己算，见
  [docs/testing/next-step.md §4.5.1](../testing/next-step.md#451-哈希怎么比才算数2026-11-14-实测踩坑)）。
- **【实测】client 半不是一个插件一个 `<script src>`。** 宿主按"组"合并下发
  `dsh-app://app/plugins/??<pkgA>/client.js,<pkgB>/client.js,...&rev=<rev>`，由
  `@deepseek-ai/dsh-client-modules` 的模块加载器取回正文并注册 factory。所以
  `document.querySelectorAll('script[src]')` 里查不到单个插件（只有 `index-*.js` 与 modules
  加载器两条），按 `script[src*="<pkg>"]` 判断"插件有没有加载"会落空；要看加载状态请用
  `window.__DSH_BOOT__.entries` 或插件自己注入的 `style[data-plugin]` 标记。

桌面回归的 4 条说明（与 rc.2 相同，仍然成立）：脚本驱动**正在运行的桌面版**（CDP 9222）而不是临时 home；默认只读；advisor 脚本会拒绝在「正在跑回合 / 输入框不可编辑 / 有别人草稿」的会话上敲键盘，但会自己挑一个**空闲会话**做 Esc 流程，所以在 agent 正在跑回合时也能跑完。

## 7. 一次瞬时失败：next-step web 冒烟首跑 2 FAIL、重跑 59/59

第一次跑 `pnpm smoke:next-step` 是 **13 PASS + 2 FAIL**（共 15 项，后面的断言因为拿不到卡片没有执行）：

```
FAIL 卡片在答后出现（conversation.chat.turnTail） :: 等 120s 后没有任何 section[data-next-step-card]
FAIL 日志里有卡片记录（可跨重启重建）              :: 期望>=1 实际=0
```

截图里能读到的现场：助手已经完整回答了「二分查找」三问（远超 `MIN_ANSWER_CHARS = 80` 的道闸），卡片位置是 **「生成下一步建议｜操作失败，请重试」**——即用户可见的兜底按钮出现、点了，但补生成调用**失败**。所以不是「回答太短被门挡」，也不像客户端没渲染。

**复跑结论**：带 `SMOKE_KEEP=1 SMOKE_DEBUG=1` 单独重跑一次，**59/59 PASS，0 SKIP / 0 FAIL**（会话日志里 `plugin:next-step/card`、`phase=sent`、胶囊 WYSIWYG 等 44 项都过了）。

**归因（2026-11-14 二次排查后更正）**：先前把这次失败写成「CPU 争抢下的瞬时失败」——**那个说法是错的**，照原样制造同样的并发负载（三个桌面回归 + 一次 web 冒烟同时跑）**没能重现**，59/59 通过。真正确定的是下面两件事：

1. **机制确定**：卡片生成走 `writeCardFor()`，用 `setTimeout(() => controller.abort(...), settings.timeoutMs)` 兜底，默认 `timeoutMs: 20000`。超时后 `generate()` 以抛错收场，`writeCardFor` 落到 `catch` 后返回 `{ok:false, reason:"aborted"}`，客户端把 `aborted` 映射成 `error.failed`「操作失败，请重试」——与截图里的文案一致。用 `timeoutMs: 150` + 一个挂起的假 `generate` 驱动真实 `writeCardFor`，得到 `{ok:false,reason:"aborted"}`、abort 的 reason 是 `next-step timeout`，**机制可确定性复现**。
2. **子原因不可恢复**：`failed / schema / aborted / not-needed` 四种原因**都映射到同一句** `error.failed`，光看界面分不出来；而中止路径当时**既不计数、也不写 `lastSkip`、更不落会话日志**（`catch` 里还有 `if (!controller.signal.aborted)` 把中止直接跳过），诊断面板显示「失败 0」。首跑没设 `SMOKE_KEEP`，临时 home（含内存态）已随进程销毁——所以**这次失败的确切子原因事后无法还原**，只能确认它不是「回答太短被门挡」（回答远超 80 字）。

**已据此改进（见本仓库下一版）**：next-step 增加 `counters.aborted` 与中止时的 `lastSkip`（超时写 `generation timeout after Ns`），失败文案改为 `error.aborted`「生成超时或被取消，请重试」；`smoke:next-step` 在没出卡时读面包屑 `data-next-step-retry-error` 把插件自报的原因打出来，并**在断言失败时自动保留临时 `DSH_HOME`**（不再只有 `SMOKE_KEEP=1` 才留现场）。下次同类失败可以直接读出是超时还是别的。

**不是 rc.3 的破坏性变化**：探针里 next-step 依赖的 seam（`turnTail` 槽、`sessionProjections.register`、`appendPluginRecord`、`llm.prepareCall` + `call.stream`、`use` 路由与 `agents.get(id).model.current()`）在 rc.3 上都还在，两次单独重跑（含一次并发负载下）都是 59/59。

排查建议：冒烟建议与桌面回归**串行**跑（都要打真实模型、都吃 CPU），但别再把它当成已证实的因果；再遇到同类失败，先看冒烟新打出的 `插件报错（没出卡时）` 与保留下来的临时 home 里宿主日志。

## 9. 插件索引源（Discover）：格式与实测坑位

2026-11-15 在 0.2.2-rc.3 上实测，配套脚本 `scripts/build-index.mjs` 与 `pnpm smoke:index`。

- **【实测】没有官方索引。** 插件市场 bundle 的 README 明说 "There is no official index; Discover lists only the index sources the user adds."；官方组合包自带的 Discover 标签页在没有任何索引源时是空状态（「添加一个插件索引，即可在这里浏览和安装其中的插件」）。
- **【事实】索引源是一份 format 1 的 JSON。** 顶层 `{ format: 1, title, description?, metadata.categories?, plugins: [] }`；`title` 为字符串或至少含 `en` 的语言表。每个 plugin 的 `name` 必须是合法 npm 包名、`versions` **必须非空**；每个版本要有精确 SemVer 的 `version`、整数 Unix 秒的 `publishTimestamp`、`source`（`{type:"npm"}` 或 commit 固定的 `{type:"git", url, commit}`）；`engines.dsh` 可选。宿主用 `@deepseek-ai/dsh-plugin-market-index` 校验，坏文档报 `plugin-market/invalid-index` 并带 JSON 路径（冒烟里把版本写成 `1.0`，页面显示「此索引的格式无效」，路径是 `$.plugins[0].versions[0].version must be an exact SemVer version`）。
- **【事实】索引 URL 的规则比想象中严。** 必须是 canonical 的 `http:` 或 `https:` 地址，**不能带用户名/密码、query 或 fragment**；宿主**拒绝跟随重定向**（`fetch` 层直接拒绝）；单次读取 `fetchTimeoutMs` 默认 15 秒、`maxBytes` 默认 128 MiB；读到的文档缓存 `cacheTtlMs` 默认 10 分钟。所以 `https://raw.githubusercontent.com/.../index.json?raw=1` 这类地址不能用。
- **【实测】jsDelivr 的 `gh` 入口不能用作索引源。** `https://cdn.jsdelivr.net/gh/<owner>/<repo>@main/...` 返回 **301 → raw.githubusercontent.com**，宿主会直接拒收；`https://cdn.jsdelivr.net/npm/<pkg>/index.json` 返回 **200、无跳转**，边缘缓存 `s-maxage=43200`（12 小时），可用 `https://purge.jsdelivr.net/npm/<pkg>/<file>` 主动失效（实测 200）。`raw.githubusercontent.com` 对现成文件也是 200、无跳转、`cache-control: max-age=300`，但国内可达性差。
- **【实测】安装状态是"索引版本 × 已装版本"算出来的。** `installed`（等于索引里的版本）、`update-available`（索引版本更高）、`different-version`（已装版本**更高**、非法 semver 或未知）、`provided`（随 DSH 提供）。所以索引过期不只是"少显示一个更新"：装过新版的用户会看到 `different-version`，点安装还会装到索引里的旧版本。**索引必须在每次发版后重建。**
- **【实测】社区事实标准索引只列 latest。** `dsh-plugin-catalog`（`https://cdn.jsdelivr.net/npm/dsh-plugin-catalog/index.json`）由 `awesome-dsh-plugin` 每晚 02:23 UTC 构建（`build-site.yml` 的 `schedule`，也是唯一发布 npm 索引的路径），每个插件只写 `dist-tags.latest` 一个版本；条目收录是每插件一条 YAML 的 PR，一次最多 3 条。
- **【实测】对话框不会自动关闭。** 添加索引源成功后「索引源」对话框仍开着，源列表里失败的那条会把宿主错误原文（含 JSON 路径）标红显示；页面主区域同时显示「此索引的格式无效 / 重试」。写冒烟时别假设它会关。
- **【实测】「开始使用」对话框会挡截图。** 临时 `DSH_HOME` 没有模型凭据时首启会弹它；它不拦程序化点击，但会把截图挡住——冒烟里先点它的 × 关掉再截图。

## 10. 第三方插件拿不到 llm adapter；Remote 方法的签名约束（btw 实测）

2026-11-16/17 写 `@kangyishuai/dsh-btw` 时逐条实测。这两条都直接影响插件架构选择，踩中会浪费很久。

- **【实测】第三方插件拿不到带 provider adapter 的 `llm` 实例。** 六种取法全部失败：
  `inject:['llm']` + `ctx.llm.stream()` → `cannot get required service "llm" in inactive context`；
  `apply()` 里同步捕获 `ctx.llm`、监听器里的 `this`（发射事件的 LlmRuntime）、`agent.ctx.llm`、
  `agent.ctx.get('llm')`、`ctx.get('llm')` + `prepareCall()` → 全部 `NO_ADAPTER: no adapter registered for provider "deepseek-official"`。
  微诊断：`ctx.llm === ctx.llm` 为 **false**（每次访问返回新代理），`adapters` 恒为空 `[]`，
  但 `listProviders()` 仍能列出 provider——**provider 目录是共享的，adapter 表是实例私有的**。
  → 想在插件里「自己拼 messages 调模型」的路走不通；可行路径是 `ctx.subagents.startActivation({ provider:'fork' })`。
- **【实测】`ctx.agents.get(sessionId)` 返回 `undefined`。** 真实 `Agent` 只能从**调用上下文**取：
  命令用 `invocation.agent`，工具用 `exec.agent`。所以需要 Agent 的功能必须挂在命令或工具上。
- **【实测】Typert Remote 方法有 SRC 签名校验，参数不能有默认值/解构/剩余参数。**
  写成 `async history(request = {})` 时调用返回
  `{"ok":false,"error":{"code":"gateway/signature-invalid","message":"typert gateway: btw/history: SRC method \"history\" must use unique identifier parameters without destructuring, defaults, or rest"}}`
  （校验点：`dsh-api-gateway/lib/index.js` 的 `SRC method ... must use unique identifier parameters`）。
  缺省值必须在方法体里兜底：`async history(request) { const input = request ?? {}; … }`。
  另：Remote 方法必须声明在**被导出的类自身原型**上（`export default ServiceClass`，不要包一层子类），
  否则 `/api/<plugin>/*` 404；运行时没有装饰器语法，用命令式 `Remote(name)(void 0, {addInitializer})` 登记。
- **【实测】客户端调 Remote 的信封**：`ctx.connection.rpc.call("/api", "<plugin>/<method>", { args: { request } })`，
  成功时解 `{ ok, value }`，失败时 `{ ok:false, error:{ code, message } }`。无构建插件没有 typert 客户端产物，
  不能用 `ctx.reflect.get("remote.xxx")`。
- **【实测】桌面/网页 composer 在没有工作区时是 `data-phase="inert"`。** 全新 `DSH_HOME` 下即使塞好了
  `storages/workspace.json`（含 `unit` 字段、路径要 `realpath`），首启仍会先弹「预览版说明」，
  不点「继续」时 composer 不可编辑；点掉之后如果工作区没被采纳，composer 会停在
  `data-placeholder="选择一个工作区开始"`、`aria-haspopup="menu"`，任何输入策略都无效。
  写冒烟时这三步都别省。

## 11. Projects 插件 M1 勘察（2026-11-16 实测）

三条新事实，都是写「按会话注入上下文 / 跨插件调服务」时踩出来的。

### 11.1 service 实例被 Cordis 包成 Proxy —— 不能用 `#` 私有成员

声明 `class X extends TypertRemoteService` 后，宿主通过 **Proxy** 暴露它。此时外部调用
`this.#requireStore()` 这类私有方法会抛：

```
TypeError: Receiver must be an instance of class ProjectsService
```

原因：私有成员要求 receiver 是类实例，而经 Proxy 调用时 `this` 是 Proxy。
**做法**：service 内部一律用普通方法（`requireStore()`），不要用 `#`；这条对
`private` 字段同样适用（`this.#x` 读改都失败）。

### 11.2 任何服务属性访问都必须先 `inject`

```js
// ✗ 抛 Error: cannot get property "agents" without inject
const agent = this.ctx.agents.get(sessionId);

// ✓
this.agents = undefined;
ctx.inject(["agents"], (scope) => {
  this.agents = scope.agents;
});
```

同理适用于 `ctx.sessionController`、`ctx.tools`、`ctx.systemPrompt` 等——**在 `apply()`
或构造函数里直接读会抛错**，且如果被 try/catch 吞掉，会表现为「功能静默不生效」。
排查建议：这类 catch 里至少 `logger.warn` 带上原文。

### 11.3 项目级上下文：按 agent 作用域注册 `systemPrompt.context`

`AssembleContext` 只有 `{ scope?, signal? }`，**没有 agent/session**。所以"只给某些会话注入"
不能靠全局 provider 判断，而要在 `agent/created` 里注册到该 agent 的作用域：

```js
ctx.on("agent/created", (payload) => {
  const agent = payload.agent;
  agent.ctx.systemPrompt.context({
    name: "projects",
    order: 120,
    text,
    required: true,
    interpolate: false,
  }); // 返回 disposer，agent/disposed 时释放
});
```

- 实测：注册后该会话的 `system/message`（持久记录）里能读到注入文本。
- 归档/解绑后要**主动 dispose**，否则在线 agent 会带着旧上下文继续跑（实测过）。
- 会话通常是「先 create（agent 立刻就绪）后归属项目」，所以归属动作必须**补挂在线 agent**，
  不能只依赖 `agent/created` 这一个时机。

### 11.4 客户端：面板注册、RPC 与字典（2026-11-16 实测）

**四个注册面（都在 `ctx.slots.inject(slot, () => ctx.slots.register(descriptor, Component))` 里）**

| 面           | descriptor 关键字段                                                 | 组件收到                                                       |
| ------------ | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| 侧栏全局面板 | `{ name:"sidebar.panellist", id, order, label:()=>string, locale }` | `{ size, active }`（图标；点击行由宿主负责，不要自己处理导航） |
| 主面板       | `{ name:"main", key, locale, inject?, store?, children? }`          | `inject()` 的返回值 + 宿主附加 props                           |
| 设置分节     | `{ name:"settings.section", id, order, label, locale, inject? }`    | 同上                                                           |
| 覆盖层       | `{ name:"shell.overlay", id, locale, inject? }`                     | 同上                                                           |

⚠️ `main` 用 **`key`**，其他用 **`id`**；写错不会报错，只是永远不出现。

**RPC 两条硬规则**

1. **一元回执包在 `value` 里**：`rpc.call("/api", "<service>/<method>", { args })` 的结果要
   `"value" in result ? result.value : result` 解包（与 session-delete 同款）。
   漏了解包会得到 `{ok,value}` 对象，表现是「列表渲染成 undefined / .map is not a function」。
2. **SRC 模式要求 Remote 方法无默认参数**：网关报
   `SRC method "createProject" must use unique identifier parameters without destructuring, defaults, or rest`。
   把 `createProject(name, input = {})` 改成 `createProject(name, input)` 并在函数体内 `input ?? {}`。

**运行时字典必须在代码里注册**

`locale/*.json` 只供插件管理器显示标题/描述；UI 文案要在 client 半
`ctx.locale.register(NS, { zh, en })` 注册（无构建插件没有生成产物）。
字典形状是**一层命名空间 + 带点的扁平键**：`{ "projects": { "panel.title": "项目" } }`，
客户端 `t("panel.title")`。写成嵌套对象会静默取到 key 本身。

**首启「预览版说明」对话框会把其余内容置为 `inert`**

临时 `DSH_HOME` 首启、或没有模型凭据时会出现。它不拦程序化点击，但会让
`element.focus()` 失效、`inert` 祖先链上出现一个 `DIV`——表现为「面板明明渲染了，但输入框收不到键盘」。
冒烟/自动化里先点它的主按钮（`[data-modal-autofocus]` 或最后一个 button）关掉再交互。

### 11.5 M2 实测：`ctx.subprocess.spawn` 的真实 spec（2026-11-16）

按印象写 `spawn({ command, args, stdio: "pipe" })` 是**错的**——宿主 spec 是：

```ts
interface SubprocessSpawnSpec {
  argv: readonly string[]   // argv[0] 是程序本身，不经 shell
  cwd: string
  stdio: SubprocessStdio    // 每流的处置；返回的 handle 带按上限采集的 stdout/stderr
  graceMs: number           // 正数、有上限，终止与排空都靠它
  signal?: AbortSignal
  env?: ...
}
```

它是**策略 seam**（超时、杀死升级、采集上限、spill 文件），返回的是采集句柄而不是裸流。
所以：

- 需要**长任务/需要被杀死的**（bash 工具、dev server）→ 用它，并自带 `graceMs`。
- 只需要**一次短命令的 stdout 与 exit code**（例如插件里调 `git rev-parse`）→
  `node:child_process.execFile` 更直接（插件本身就跑在宿主的 Node 进程里）。
  本插件的 `createThread`/`reclaimThread` 走后者，并在代码注释里写明了理由。

附带两条与 `inject` 有关的时序事实（同一轮踩到）：

1. `ctx.inject(names, cb)` 的回调是**异步**的：服务刚构造完成、回调还没跑时，
   外部（例如另一个插件的 `inject(["projects"], …)`）就可能调用本服务的方法。
   所以「构造期把服务存进字段」不够，需要 **就绪 Promise + 超时**兜住这个窗口。
2. 忘记 inject 某服务时，`this.x` 是 `undefined` 而不是抛错——因为这**不是**属性访问，
   是读自己字段。表现是「方法直接报 unavailable」，很容易误判成宿主没这个服务。

### 11.6 一轮的「成败」到底记在哪（2026-11-16 实测）

用真实会话抓完整事件序列（成功的一次）：

```
step/start → system/message → user/message ×4 → request/header → request/context
→ session/title → session/title-llm-request → session/title → assistant/message
→ step/end → turn/end { turn: 1, reason: { kind: "completed" } }
```

结论：

1. **`turn/end` 的 payload 只有 `{ turn, reason }`**，成功时 `reason.kind = "completed"`；
   失败时（M0 实测的 `MISSING_CREDENTIAL`）错误出现在 **`assistant/attempt` 的
   `stream[].chunk.type = "finish"` 的 `reason.kind = "error"`** 里，
   而不是 `turn/end`。
   → 想判「这一轮失败了」必须**记住本轮 attempt 的失败**，在 `turn/end` 时合并；
   只看 `turn/end` 会把失败当成功。
2. 一次 prompt 会带出 **4 条 `user/message`**（用户输入 + 会话上下文 reminder + 技能清单 +
   时间上下文），所以「有没有用户发言」必须判 `source.kind`，不能数条数。
3. `session/title` 有两次：先 `fallback`（截断首条消息），再 `provider`（模型生成）。
   标题生成**本身是一次模型调用**（`session/title-llm-request`）——只想"让会话非空白"的冒烟
   会顺带触发这次调用，写冒烟时要意识到这点。

### 11.7 归档是 workspace 事件，不是 session 事件（2026-11-16 实测）

`dsh-session` 的 63 个会话事件里**没有** `archived` 之类的类型（只有 `feedback/message-delete` 与归档沾边）。
归档发生在 workspace 子系统，可用的是 **Host 分派事件**：

| 事件                            | 模式     | 用途                                       |
| ------------------------------- | -------- | ------------------------------------------ |
| `workspace/session-archived`    | parallel | 会话已进入归档集合；插件据此做"归档后清理" |
| `workspace/session-stop`        | parallel | 带 `stopActivity` 归档时先停其工作         |
| `workspace/session-unarchiving` | parallel | 取消归档前的前置/收尾                      |

签名都是 `(request: SessionActivityRequest) => Promise<void> | void`，`request.sessionId` 是受影响的会话。
实测：在 `workspace/session-archived` 里回收 worktree，归档完成后 4 秒内 `projects.json` 的
`threads[sessionId].worktree` 已变成 `null`，`git worktree list` 里对应条目消失。

### 11.8 唤醒链路实测（2026-11-16）

把「线程跑完一轮 → 给协调器一封带结果的信封」这条链在真机上跑通，关键事实：

1. **协调器会话就是普通会话**：`sessionController.create({ cwd })` 建出来即可，
   把 id 存进项目记录（`coordinatorSessionId`）。不需要特殊 role。
2. **投递信封用 `sessionController.prompt`**，`content` 里放一段文本就够了；
   信封里的 `report`（线程最后一条 `assistant/message` 的文本）**必须带**，
   否则协调器会答「读不到它的输出」（M0 已证）。
3. **同一轮只唤醒一次**靠业务状态（线程记录上的 `lastWakeTurn`）而不是靠事件次数：
   `turn/end` 只发一次，但重启/重连都可能重放，所以判据要落在持久记录上。
4. 没配协调器时**不要静默**：记一条 `wake/skipped { reason: "no-coordinator" }` 审计，
   这样用户能看出「为什么没有反应」。
5. 顺带验证：失败的一轮在 `progress` 里确实报 `failed`（§11.6 的修正成立）——
   之前只看 `turn/end` 会把它当 `done`。

### 11.9 自治级别闸门与路由审计实测（2026-11-16）

同一句话（"implement the payments webhook with retries"）在两个自治级别下的实测结果：

```
L1 → { executed: false, by: "blocked", action: "new-thread", ruleId: "long-task",
       reason: "autonomy/L1" }   线程数不变
L2 → { executed: true,  by: "rule",    action: "new-thread", ruleId: "long-task" }
      现场建出线程，线程数 +1
```

结论（写进实现的两条）：

1. **级别闸门放在决策之后、执行之前**：先算「想做什么」，再问「这个级别允许吗」。
   这样审计里能同时看到意图与拒绝原因，用户改级别后也知道会发生什么。
2. **被拦不是错误**：`route` 正常返回 `executed: false` + 原因，不抛异常。
   抛异常会让调用方（面板/协调器）把它当故障处理，而它其实是**设计好的保守行为**。

审计形状（每条路由一行，可读、可回放）：

```jsonc
{
  "action": "route",
  "projectId": "prj_x",
  "input": "前 120 字",
  "decision": { "by": "rule", "action": "new-thread", "ruleId": "long-task" },
  "autonomy": "L1",
  "result": "blocked",
  "reason": "autonomy/L1"
}
```

### 11.10 给会话挂「人格」：agent 是懒创建的（2026-11-16）

想给协调器会话挂 `systemPrompt.context(...)`（人格段落），踩到一条时序事实：

- 用 `sessionController.create({cwd})` 建出会话后，**agent 还不存在**；
  `agent/created` 要等这个会话真正开始一轮才触发。
- 所以「在 create 之后立刻挂载」拿不到 `agent`；「只靠 agent/created 钩子」又会
  受订阅时序影响（实测：协调器会话跑过一轮，但人格没挂上，审计里只有 `coordinator/created`）。
- 可靠做法：**建完主动预热一轮**（`sessionController.prompt` 一句轻量文本），
  然后在几秒内轮询 `ctx.agents.get(sessionId)`，拿到 agent 就 `systemPrompt.context(...)`。
  实测 4s 内拿到，审计出现 `coordinator/persona`。
- 拿不到时**不要静默**：记 `coordinator/persona-skip { reason: "agent-not-ready" }`。

这与 §11.5 的 `inject` 异步是同一类问题：**DSH 里「对象建好了」不等于「对象可以用了」**，
凡是「建完立刻要挂东西」的地方，都要有就绪判据（Promise 或轮询 + 超时），并把失败记成可观测的审计。

### 11.11 `tools.register` 的 registration 契约（2026-11-16 实测源码）

宿主 `dsh-tools` 的 `register(definition, options)` 实际校验（源码摘录，非猜测）：

```js
const output = definition.output;
if (
  output === undefined ||
  typeof output !== "object" ||
  typeof output.render !== "function" ||
  (output.presentationMeta !== undefined && typeof output.presentationMeta !== "function")
)
  throw new TypeError(`tool "${name}" must declare output { schema, render, presentationMeta? }`);
assertSupportedJsonSchema(output.schema);
```

要点：

1. **`render` 必须在 `output` 里**，且是函数。放在工具顶层不会被看到（我第一次就踩了这个）。
2. **`presentationMeta` 如果给，必须是函数**，不能是 `{ verb, object }` 这种对象
   ——报错文案读起来像「你漏了 output」，其实是你把可选字段填成了错误类型。
3. `output.schema` 会过 `assertSupportedJsonSchema`，所以必须是受支持的 JSON Schema 子集。
4. **失败要写进审计，而不是只打日志**：宿主默认不显示插件日志，
   我最初只 `logger.warn` 时，真机上完全看不出「工具没挂上」；改成
   `coordinator/tools-skip { reason }` 之后一眼定位到上面这行报错。
   这与此前 `wake/sent`、`wake/skipped` 同一原则：**插件自己装不上的东西，用户必须看得见**。

### 11.12 token 用量：`assistant/message.usage` 实测常常缺席（2026-11-16）

给「项目级 token 预算」找数据源，实测结论：

- 类型上 `assistant/message` 事件**可以**带 `usage`（`TokenUsage { inputTokens, outputTokens, totalTokens?, cacheRead/Write? }`，
  见 `dsh-llm/src/types.ts`），文档说"适配器上报时才有，不存在独立的 usage 记录"。
- 但真机跑一轮（真实凭据、真实模型调用、成功返回 `OK`）时，该事件 **没有 `usage` 字段**：
  抓到的 14 条事件里 `usages: []`。
- `ctx.tokenMeter` 提供的是 `measure(session, header)` / `contextPressure(session)` / `estimateMessage(message)`，
  即**当前上下文的测量**，不是「这一轮花了多少」的累计账本。

所以：

1. **不能**假设 `assistant/message.usage` 一定有值——按「有就累计」写，缺了就跳过，别把 0 当真实花费。
2. 想做「真实花费上限」，得先确认该路由/适配器是否上报 `usage`；若不上报，
   只能用 `tokenMeter.estimateMessage` 估算（并明确告知用户这是估算）。
3. 本插件当前的处置：token 分桶与闸门逻辑**已实现且有单测**，累计入口挂在 `assistant/message.usage` 上；
   在没有上报的来源下它保持 0，闸门不会误伤。等找到可靠来源再接。

### 11.13 Remote 方法的返回值会丢 `undefined`（2026-11-16 实测）

客户端半通过 RPC 读 Host 的 Remote 方法时，`undefined` 会被序列化成 `null`。

- 踩点：探针里写 `const p = await projects.getProject(id); const gone = p === undefined`，
  在项目**确实已删除**的情况下得到 `gone === false`（实际拿到的是 `null`）。
- 影响：凡是「用 `=== undefined` 判断存在性」的断言/分支，在 client 半与 RPC 调用方都会失效。
- 做法：**存在性用集合判断**（`listProjects().some(p => p.id === id)`），
  或显式写成 `value === undefined || value === null`。
- 同类：`getProject` / `getProjectContent` 这类「找不到就返回空」的方法，
  在 RPC 边界上要按 `null` 处理。

另外这条也提醒：**真机断言要避免依赖「空值语义」**，优先用「列表里有没有」这种结构性事实。

### 11.14 用本地 bare 仓库验证「推分支」这条远端路径（2026-11-16）

不需要 GitHub、不需要网络、不需要凭据，就能把「插件真的推了分支」验证到底：

```bash
git init --bare /tmp/remote.git
git -C /path/to/repo remote add origin /tmp/remote.git
# 插件执行 push 之后
git -C /tmp/remote.git branch --list      # 应能看到 dsh/... 分支
```

实测结果（`executeApproval` 的 `push-branch`）：

- 只推 `dsh/` 前缀且字符集合法的分支（`planCommand` 白名单），其它分支名直接拒绝；
- 用 argv 数组调 `git`（不经 shell），工作目录是**该线程的 worktree**；
- 成功/失败都写审计，并附恢复证据 `{ action, at, branch, remote }`；
- 无 worktree 时直接返回 `no-worktree`，不去猜目录。

这条技巧对任何「要写远端但不想污染真实仓库」的验收都有用：**远端可以用本地 bare 仓库顶替**，
除了 `gh`（PR）之外，`git push` / `fetch` / `worktree` 全都能这样端到端验证。

### 11.15 「分支已合并」在 squash-merge 仓库里不是可靠清理判据（2026-11-16）

想给「归档线程时清理本地分支」找回依据，实测两条都不可靠：

1. **没有提交的分支**：`git branch --merged HEAD` 会把「指向与 HEAD 同一个 commit」的
   新建分支列为已合并 → 判定"可删"。删掉确实无害，但它并不是"PR 已合并"的证据。
2. **squash merge 之后**：squash 在目标分支上生成**新 commit**，源分支的原始提交从未进入
   目标分支的历史 → `git branch --merged` 会把已经合并掉的分支判成**未合并**，
   于是永远不清理。本仓库（以及多数用 squash 的项目）正属于这一类。

结论：**不要用 `--merged` 作为自动删除分支的依据**。可选做法（都要求额外信息）：

- 已推送的分支：用 `git rev-list --count origin/<base>..<branch>` 或
  `git cherry -v <base> <branch>` 判「提交是否都以等价形式存在」——但 squash 后仍需
  `git cherry` 的 `-` 标记才可靠；
- 有 PR 的场景：以 PR 状态（merged）为依据，而不是本地 git 启发式。

本插件的处置：`shouldDeleteBranch` / `cleanupThreadBranch` 保留为**未接线的工具函数**
（有单测，判据明确要求「已合并 + 无未推送 + 非当前分支」），但**不自动执行**；
等有 PR 状态来源后再接。默认行为仍是"只保留、不删除"。

### 11.16 桌面端回归为什么在本地跑不起来（2026-11-16）

### 11.17 插件里的两类并发陷阱（2026-11-16，真机验证）

插件跑在长驻宿主里，同一入口会被多条路径同时调用，实测踩到两类：

**① 「没有就创建」要单飞**
`ensureCoordinator` 原本是「读记录 → 没有就建 → 写记录」。面板、探针、唤醒路径并发进来时
各自读到"没有"，于是建了多份协调器会话（多花一次会话、人格挂到孤立会话上）。
做法：per-project 的**在途 Promise**——并发调用复用同一个创建，完成后从表里删掉；
失败也要删，否则一次失败会把该项目永久卡住。

**② 幂等判定必须排在「资源是否还在」之前**
`executeApproval` 原本先 `getProject(approval.projectId)`。但 `delete-project` **执行成功后项目就没了**，
第二次调用于是抛 `unknown project` ——把「重复执行」误报成「项目丢了」，
调用方会以为是数据损坏而不是重复请求。
正确顺序：查申请 → **判已执行（幂等返回）** → 查项目（缺失则 `project-missing`）→ 闸门 → 占位 → 执行。

真机结果（并发 3 次 `ensureCoordinator` + 同一审批执行两次）：

```
sameSession: true, createdAudits: 1
firstExecuted: true, secondRefused: true
```

### 11.18 在 `agent/created` 里挂 `systemPrompt.context` **不会**进入模型提示词（2026-11-16 实测）

这条推翻了 M1 时的假设，必须记下来。

实验（临时 DSH_HOME + 真实宿主）：在 `agent/created` 回调里注册两段独一无二的标记：

- A 入口：`agent.systemPrompt.context({name, order: 900, text: MARKER_A, interpolate: false})` → 调用成功（返回 undefined 的 disposer）
- B 入口：`agent.ctx.systemPrompt.context({...order: 901...})` → 调用成功（返回函数）
- 同时把 `instructions.md` 写到项目目录（`getProjectContent` 能读回，说明文件路径没问题）

结果：该会话**所有事件**里都搜不到 A、B 与 instructions 的标记；`system/message` 长度 6151 与未挂载时一致。
服务侧 `attached` 映射确实记录了这条会话（说明我们的注册代码被执行了）。

线索：agent 对象上有 `frozenMessages`、`requestSurfaceGeneration` 字段——
强烈提示**提示词在一次请求开始时就冻结/组装好**，之后再注册的系统提示片段不会被回收进本轮。

**结论**：想注入项目上下文，必须在**本轮装配之前**完成注册，而不是在 `agent/created` 里补挂。
下一轮要验证的候选 seam（按可能性排序）：

1. `session/created`（会话刚建立、还没跑第一轮）——最可能正确；
2. 插件自身 ctx 上的 `systemPrompt.context` **按会话作用域**注册（若支持 session 级 scope）；
3. `agent/pre-step` 里注册（更晚，可能也来不及）。

同时修掉一处**假装成功**：`attachProjectContext` 在拿不到 `systemPrompt.context` 时原本返回
`{dispose: () => {}, text}`，调用方会把假 disposer 记进 `attached`，于是"看起来挂载成功、实际一条都没进模型"。
现在改为返回 `undefined`，让调用方如实记录失败。

### 11.19 `systemPrompt` 的 API 地图与「动态上下文」的正确用法（2026-11-17，读源码 + 实测）

`dsh-system-prompt`（`@deepseek-ai/dsh-system-prompt/lib/index.js`）暴露的方法只有这些：

```
section / getSectionOrder / context / getContextOrder / suppressRuntimeContext / tools / variable / refreshContext
```

**读源码得到的四条硬事实：**

1. **服务必须先 `inject`**：从插件 ctx 直接 `ctx.systemPrompt` 会抛
   `cannot get property "systemPrompt" without inject`（实测确认）。要先 `ctx.inject(["systemPrompt"], …)`。
2. `context()` 只校验 `order` 是有限数字；**不校验 `text` 类型**——这是坑的源头。
3. **首次装配**走 `renderContextSections(assembly)`：它直接对 `context.text` 取 `.length` 与做插值，
   所以 `text` 若是函数会被当成空（函数 `.length` 是形参个数），条目被静默过滤。
4. **但刷新路径** `refreshContext(assembly, context)` 用的是 `resolveContext(provider, context)`，
   里面**支持** `typeof entry.text === "function"` 并按当前 context 求值；
   且 `required: true` 的条目在抑制时仍会被保留、缺失时会按 order 补回。

**结论（对插件的要求）：**

- 想要「每步/每次请求都重新求值」的上下文，正确写法是
  `ctx.inject(["systemPrompt"], ...)` → `context({ name, order, required: true, interpolate: false, text: () => ... })`，
  并确认走的是 `refreshContext` 那条路径；**首次装配**仍需要字符串（可给函数同时保证首次有值，
  或首次给字符串、之后靠 refresh 更新）。
- **不要**在 `agent/created` 里注册——实测无效（§11.18），提示词在那之前已冻结。
- 用函数 + `interpolate: false` 时注意：不要指望 `renderContextSections` 会调用你。

这条把「项目上下文注入」的修复方向从猜测收敛成一个具体写法，下一步按它改并复验。

### 11.20 项目上下文注入的**正确机制**（2026-11-17 真机验证通过）

§11.18 记录的失败（per-agent 注册无效）已定位并解决。可用写法只有一条：

```js
ctx.inject(["systemPrompt"], (scope) => {
  scope.systemPrompt.context({
    name: "projects",
    order: 120,
    required: false,
    interpolate: false,
    text: (context) => renderFor(context?.agent?.session?.id), // 关键是**函数**
  });
});
```

要点（每条都经实测/读源码确认）：

1. **必须 `inject(["systemPrompt"])`**，否则 `cannot get property "systemPrompt" without inject`。
2. **在插件 ctx（全局）注册一次**，不要 per-agent；`agent/created` 时注册进不了提示词。
3. **`text` 用函数**：宿主 `refreshContext → resolveContext` 会用当前 context 调用它；
   函数里从 `context.agent.session.id` 取会话，未归属/已归档就返回空串（等于不注入）。
4. `interpolate: false`：项目文本里全是用户自己的措辞，不要做变量插值。
5. 注入结果**落在 `user/message`（运行时上下文提醒）里，不是 system message** ——
   所以验证时要扫该会话的全部事件，只看 `system/message` 会误判为"没注入"（我就是这么误判了一轮）。

实测证据（临时 DSH_HOME + 真实宿主，项目线程第一轮）：

```
instructions.md 写入 INSTR-MARKER-9f3a → markerInEvents: ["instr:user/message"]
appendMemory 写入 lazy-memory-marker   → markerInEvents: ["mem:user/message"]
```

同时删掉了 per-agent 挂载路径（它既无效、又会与全局条目重复注入），
`attachProjectContext` 与相关测试一并移除；现在只有 `registerProjectContext` 一条机制。

### 11.21 全局上下文的会话边界：线程 ✅、普通会话 ✅、协调器 ❌（2026-11-17 实测）

用 §11.20 的全局注册 + 按会话求值，实测三类会话：

```
thread: true          # 项目线程：项目上下文（instructions + memory）出现在 user/message
plain:  false         # 不属于任何项目的普通会话：没有任何注入（全局条目按会话过滤生效）
coordinator: false    # 协调器会话：渲染器匹配到了（renderStats.coordinator=12），但提示词里没有
```

诊断数据（`describe().renderStats`）：`{call: 23, thread: 9, coordinator: 12, unmatched: 2}` ——
渲染器**确实**认出了协调器会话并返回了文本，但该会话的 `user/message` 里没有运行时上下文提醒
（线程会话有）。

推测与下一步：协调器会话是用 `sessionController.create({cwd})` 建的**裸会话**，
没有挂进 workspace（`workspaceRegistry.create` 建的是"目录级工作区"，会话要用 `attachSession` 挂进去）。
运行时上下文可能只为"正常工作区会话"装配。下一步：把协调器会话挂进对应目录的 workspace 再复验；
若仍不生效，则改为「协调器也走线程式上下文」（把它当作线程登记）。

当前结论：**项目线程的注入是可靠的，普通会话不被污染**；协调器拿不到上下文/人格是已知缺口，
已在 README 标注。

### 11.22 把协调器会话挂进 workspace **不能**解决它的上下文问题（2026-11-17 负结果）

按 §11.21 的推测做了实验：`ensureCoordinator` 里用
`workspaceRegistry.create(cwd, projectName)` + `ws.attachSession(sessionId)` 把协调器挂进对应目录的 workspace。

结果：

- 挂载**成功**（审计 `coordinator/workspace: attached`，连续 3 次都是 attached）
- 协调器会话依然**没有**运行时上下文提醒，`markerInEvents` 仍缺协调器
- `renderStats` 不变（`coordinator: 12` 匹配，提示词没收到）

结论：**"裸会话"不是原因**。协调器拿不到上下文的原因在别处（可能是协调器会话的提示词装配走了不同路径，
或运行时上下文提醒只为特定 agent 类型添加）。该负结果已记录，避免以后重复这条路。

保留这次的改动：把协调器挂进 workspace 本身是有价值的——它让协调器会话出现在侧栏、可被用户直接打开，
也让它和线程一样受 workspace 生命周期管理（归档/停止活动等）。

### 11.23 三层堆叠分支 rebase 的踩坑记录（2026-11-17）

背景：`feat/projects-*` 三个分支互相堆叠（M1 → M2 → M3），main 期间合并了别的插件（`packages/btw`），

**顺序与命令**（旧引用直接用远端已推送的分支做分界）：

**四个教训：**

1. **`package.json` 的脚本冲突要"两边都留"**，且要回头检查被重放的那次提交的意图是否还在

### 11.25 协调器拿到项目上下文的正解：随 wake 信封送到（2026-11-17 真机通过）

§11.21–§11.24 证明「靠宿主 runtime context 给协调器注入」这条路走不通（渲染发生了、但没投递）。
换一条路立刻成立：**把项目规则与记忆索引放进 wake 信封**。

实现：

- `buildEnvelope({ ..., context })` 新增可选的 `project` 段（`project-context:` 前缀，上限 2000 字符）；
- `maybeWakeCoordinator` 用 `renderProjectContextFor(project)` 读 `instructions.md` + `memory/MEMORY.md` 放进信封；
- 不可信来源的 `context` 同样走 `wrapUntrusted` 包成数据块（和 `report` 一致）。

真机证据（临时 DSH_HOME + 真实宿主）：

```

envelopeHasMarker     : true    # 信封里带上了 MEMORY.md 的标记文本
```

这条比"再挖宿主装配条件"划算得多：信封是本插件自己的接口（§11.8 已验证可达），
把上下文挂在信上既确定了送达时机（每轮 wake 一次），也顺带避免了"每次请求都注入"的 token 成本。

### 11.26 人格同样随信封送达（2026-11-17 真机通过）

人格原本走 `systemPrompt.context`（与项目上下文同一条失效路径，§11.24）。改为挂到 wake 信封：

- `buildEnvelope({ ..., persona })` 新增 `persona` 段（上限 1200 字），排在 `project` 之后、`report` 之前；
- `maybeWakeCoordinator` 里用 `buildPersona({ projectName, persona })` 生成，随信送达。

真机验证（三种标记同时检查）：

```

envelopeHasMarker     : true    # 项目记忆标记随信到达
envelopeHasPersona    : true    # 人格文本随信到达
```

至此协调器的输入不再依赖宿主 runtime context：**项目上下文 + 人格 + 线程结果**都在同一封信里，
送达时机确定（每轮 wake 一次），也让"人格不改变权限"这句话能被稳定地送到模型面前。

副作用（可接受）：信封变长（上下文 2000 + 人格 1200 + 报告 800 字符上限）。若将来 token 敏感，
先把 `project-context` 换成"索引摘要 + 让协调器用 project_memory_read 取详情"。

### 11.27 共享文件反复冲突：正确解法是「取 main 版本 + 精确注入」

§11.23 记了第一次 rebase。第二次对齐 main 时又撞了**同样四个文件**
（`package.json`、`scripts/index-meta.json`、`.github/labeler.yml`、
`.github/ISSUE_TEMPLATE/bug_report.yml`，外加根 README 的插件清单表）。

**踩到的坑**：用「把冲突两段文本直接拼接」的脚本处理 `scripts/index-meta.json`，
拼出来的 JSON 不合法（插件对象是多行结构，拼接破坏了括号）——`pnpm verify` 才报出来。

**可复用的正解**（每个文件都用同一种思路）：

1. `git checkout --ours <file>` —— rebase 时 `--ours` 是**目标分支（main）**的版本；
2. 用脚本把**自己的条目**精确注入：
   - `package.json`：解析 JSON、把 `smoke:projects`/`gate:projects` 等键 `setdefault` 进去；
   - `scripts/index-meta.json`：解析 JSON、`plugins["@kangyishuai/dsh-projects"] = {...}`；
   - `.github/labeler.yml`：追加以 `"plugin:projects":` 开头的块；
   - `bug_report.yml`：在插件下拉的 `- other` 之前插一行；
   - 根 README：在 `advisor` 行后插入一行表格（插完跑 `pnpm format` 对齐列宽）。
3. 每次改完立刻 `python3 -c "import json; json.load(...)"` 校验 + `pnpm verify`。

另外：**只做格式化的提交在 rebase 时常常变得多余**，`git rebase --skip` 掉比解冲突更省事
（但要确认它真的只含格式改动）。

这样处理的好处是**结果确定**：main 侧的新内容（例如后来加入的 `btw`/`artifacts` 条目）全部保留，
自己的条目也不会因为 hunk 顺序变化而丢失。

### 11.28 auto PR 链路端到端验证（2026-11-17，桩 gh + 本地 bare 远端）

开 PR 需要 GitHub，但整条链路可以**零网络**验证：远端用本地 bare 仓库顶替（§11.14），
`gh` 用 PATH 上的桩脚本顶替（记录 argv、回显假 PR URL）。

实测（`openPr`）：

```
commitCount : 1                       # 线程分支相对 base 有 1 个提交（用 git rev-list 现数）
offAction   : "none"                  # 档位 off → 什么都不做
opened      : true
prNumber    : 4242                    # 从桩 gh 的 stdout 解析出来
draftFlag   : true                    # draft 档 → argv 里带 --draft
```

桩 gh 实际收到的命令：

```
pr create --head dsh/pr-probe-…-1 --title "dsh: …" --body "Automated by the **projects** plugin …"
```

**两个实现要点：**

1. **线程上没有 commits 字段**，判定前必须现数：`git rev-list --count <base>..<branch>`；
   否则任何线程都会被判成「没有提交」，档位永远不会触发（这是我第一版的真 bug，靠真机发现）。
2. 分支名按项目名生成，**同名项目重复创建会因分支已存在而 worktree 退化**（`worktree add -b` 失败→降级共享目录），
   于是"没有 worktree 就没有可推的分支"。测试/探针要用唯一项目名，这也是 M2 降级设计的一个现实后果。

`gh` 调用与 `git` 调用统一走 `lib/exec.js` 的 `runCommand`（4 项单测：参数原样传递、失败不抛、cwd 生效、命令不存在）。

### 11.29 `merge` 真实执行与"只合并自己的 PR"（2026-11-17 真机，桩 gh）

`executeApproval` 的 `merge` 分支不再是"延期"，会真的调 `gh pr merge`：

```
开关 autoMerge=false（默认） → executed:false, reason:"switch-off"   # 开关没开根本走不到执行
开关 autoMerge=true          → executed:true
  证据 evidence = { action:"merge", prNumber:4242, revertHint:"gh pr revert <n>" }
  桩 gh 实际收到：pr merge 4242 --squash
```

要点：

1. **argv 固定为 `pr merge <n> --squash`**，不带 `--admin`、不带 `--delete-branch`、不带 `--force`——
   `planCommand` 只接受正整数 PR 号，且动作↔开关键经显式映射（`merge → autoMerge`），不存在"打开别的开关就能合并"。
2. **执行前先过四道闸门**：已批准 → 白名单 → 开关打开 → 影响面在阈值内；任一条不过就写
   `approval/execution-refused` 并附原因。
3. **幂等占位在最前**：同一申请执行两次第二次直接 `already-executed`（§11.17）。
4. 失败会写 `approval/execution-failed` 并带 stderr 第一行，不会静默。

至此 M4 的"远端写入"链路（推分支 → 开 PR → 合并）三条都在本机完成了端到端验证
（远端用本地 bare 仓库、`gh` 用 PATH 桩脚本），只剩"真实 GitHub 上的最终效果"需要一次人工发版后确认。

### 11.30 Remote 方法签名里**不能写行内类型注释**（2026-11-17 实测）

给 `archiveProject` 加上取消归档能力时，因为 TS 报隐式 any，我顺手把类型写成行内注释：

```js
archiveProject(/** @type {string} */ id) { … }   // ❌ 网关拒绝
```

运行时（不是编译期）报：

```
typert gateway: projects/archiveProject: SRC method "archiveProject"
must use unique identifier parameters without destructuring, defaults, or rest
```

**根因**：typert 的 SRC 生成器解析参数表时，把 `/** … */ id` 当成了「解构/复杂参数」而拒绝注册端点。
于是 UI 点归档时 RPC 直接 404/报错——而**单测和 `pnpm verify` 都发现不了**（它们不经过网关）。

**正确写法**：类型放到方法上方的 JSDoc：

```js
/** @param {string} id */
archiveProject(id) { … }   // ✅
```

这条与 §11.4（Remote 方法不能有默认参数/解构/rest）是同一族约束的补充：
**参数表必须是「裸标识符」，连注释都不能夹在括号里**。

顺带记一个排查经验：`apps/web` 侧详情页原本**没有错误锚点**，所以「点了没反应」看不到原因。
补上 `data-projects-detail-error` 之后，冒烟立刻把上面这行网关报错打了出来——**错误要能被断言看见**。

### 11.31 冷会话唤醒：应用关着时欠下的信封要在启动后补发（2026-11-17 真机通过）

原本 wake 只在 `turn/end` 触发。于是有两条会丢信件的路径：

1. 应用关着时线程跑完 → 没有 `turn/end` 监听者，协调器永远不知道；
2. 线程跑完时**还没有协调器** → 写 `wake/skipped`（reason: `no-coordinator`）后就不管了。

补法：`reconcileWakes()` 在服务就绪后延迟 5 秒跑一次（等视图有数据），对每个 active 项目：

- 取线程列表与已知视图；
- 纯函数 `pendingWakes(threads, views)` 算出「水位落后且处于 done/failed/waiting-user」的线程；
- 逐条走 `maybeWakeCoordinator()`（内部仍由 `decideWake()` 三态去重）。

真机验证（模拟"先跑完、后建协调器"）：

```
skippedWithoutCoordinator : 1     # 线程完成时没有协调器，唤醒被跳过
scanned                   : 229
woken                     : 1     # 启动对账补发
sentAfterReconcile        : 1     # 协调器真的收到信封
```

注意 `working`/`idle` **不算欠唤醒**：补了也没有信息量，只会多烧一次协调器回合。

另一个已修的竞态：两个并发 `turn/end` 会在水位写回前同时通过检查，导致重复信封。
现在用同步 guard（`decideWake` → `skip-dedupe`）闭掉，并有单测覆盖三态。
