### 5.1 桌面回归的两个视图前置（本轮都踩到了）

桌面回归驱动的是**正在运行的那个桌面版**，脚本读的是「当前可见会话」。agent 在自己的会话里跑回归时，有两个前置必须自己先摆好：

1. **可见会话不能是「正在跑回合」的会话。** 否则 advisor 脚本按设计不敲键盘：`FAIL 当前会话空闲（没有正在跑的回合）` + 13 条 SKIP。做法：先把可见会话切到一个**空闲会话**再跑（切换只是换视图，不会中断正在跑的回合，[rc.3 §6](0.2.2-rc.3.md#6-本机实测2026-11-14) 已实测）。
2. **上一条桌面回归不能把页面留在别的页面。** casefile 的桌面回归结束时按了 Esc（断言「页面仍可用」），但**不会离开「案卷」主面板**；紧接着跑 btw 会因为没有 composer 而报 `FAIL 输入框左侧出现 btw 按钮`（本轮首发就是这个假红，重跑前先切回会话即 18 PASS / 1 SKIP）。串行跑多条桌面回归时，**两条之间先点回任一会话**。

这两条都不是 rc.5 的破坏性变化，是「谁在跑回归」的环境问题——写进了 §7 的升级清单。

### 5.2 命令卡片只在**非空白会话**里渲染（2026-11-20 实测）

排查 `smoke:btw --deep` 的两条 SKIP（「回车后聊天流出现节点」「提交 /btw 后出现命令卡片」）时确认的宿主行为：**在全新（blank）会话里提交一条不产生回合的斜杠命令，命令会在宿主执行、结果落进会话日志与插件数据，但客户端一个 `[data-chat-flow-kind]` 节点都不会渲染。**

证据链：

1. **命令确实执行了。** 临时 `DSH_HOME` 的会话日志里有 `command/run` → `command/done`（`kind:"success"`，`text:"OK\n\n— btw · new 1.5K tokens · cached 9.2K · 1.5s"`），插件 history 也有 `status=done` 的记录；同一条会话里**没有** `turn/start` / `user/message`（命令是 log-only 追加，不包回合）。
2. **页面停在 hero 空态。** 提交前后 `body` 长度都是 ~130 字符、`[data-chat-flow-kind]` 数量为 0；`data-phase` 是 `hero`。整页刷新、手动点侧栏那一行「新会话」也一样。
3. **发一条普通消息就全好了。** 在同一会话里发一句 `hi`（一次真实的模型回合）后：`data-phase` 变 `active`，**之前那 3 条命令卡片一次性回溯出现**（两条 `--deep` 的 `/btw` + 一条无参 `/btw`），随后新提交的 `/btw` 立即渲染成第 4 张卡片。

客户端源码对得上（`@deepseek-ai/dsh-client-ui-conversation` 的 sourcemap 里有原始 TS）：

- `contract/snapshot.ts` 的 `conversationPhase()`：`active` 只在「有 activeTargets / 会话不 blank 且不在等首回合 / 正在跑回合」时成立，否则是 `blank` / `engaging`；
- `skeleton/ConversationMainPanel.tsx`：`shellPhase === 'blank'`（且会话已 open 或列表摘要 blank）就直接走 hero，**不渲染 `conversation.session` 的 views**，所以命令节点连构建机会都没有。

**结论与用法：**

- 这是**通用宿主行为**，与 btw 插件无关（命令卡片由宿主的 `conversation-nodes/command.ts` 统一构建；`recordInput: false` 只影响 `command/run.args` 是否记录，不影响渲染）。
- 想在自动化里断言「命令卡片」，会话必须**先 materialize**（至少一个真实回合）；否则断言必然空转。`smoke:btw --deep` 已改成先发一句 `hi` 热身再提交，两条 SKIP 变成真实 PASS（30 PASS / 1 SKIP / 0 FAIL）。
- 反过来，插件**不能假定**自己的 `/命令` 输出在空白会话里可见：用户在新会话里敲 `/btw` 只会看到「什么都没发生」（输出只在会话日志 / 插件面板里）。插件若需要可见回执，只能靠自己的 UI 面（btw 的右侧栏就是这个形态）。

## 6. 本轮的工具链与文档修复

### 6.1 `session-delete` 桌面回归：空回收站会假红

`pnpm smoke:session-delete-desktop --require` 在回收站**为空**时报：

```
FAIL 回收站面板保留全选与批量操作 :: {"hasTabs":false,"hasBatch":false,"text":"会话回收站回收站是空的。关闭"}
```

**根因在脚本，不在插件**：插件的回收站面板在 `entries.length === 0` 时只渲染空态（「回收站是空的。」），工具条（全选 / 恢复（n）/彻底删除）与条目行都在 `entries.length > 0` 分支里。断言把「有空条目时才存在的东西」写成了无条件断言，于是回收站空时必红；「条目：标题可读」那条更糟——`rows === 0` 被写成通过，等于**什么都没验证还报绿**。

修法（只改脚本）：用面板里的 `.dsh-sdel-row` 数量判断空/非空，空时两条记 **SKIP** 并给出原因，非空时断言不变（更严格，去掉了 `rows === 0` 的假通过）。修后实测 **16 PASS / 2 SKIP / 0 FAIL**（`pnpm gate session-delete` 不再假红）。

### 6.2 四条桌面脚本补打印门禁依赖的计数行

[plugin-conventions §6.1](../plugin-conventions.md#61-桌面端自动化测试是硬性要求) 要求桌面脚本收尾打印 `N PASS / M SKIP / K FAIL`，`scripts/gate.mjs` 的 `parseCounts()` 靠它识别「跑过但一条断言都没执行」的假绿。本轮实测：**只有 `smoke-btw-desktop` 打了这一行**；advisor / next-step / session-rewind / casefile、以及**本轮修好的** session-delete 都没有打，`parseCounts()` 返回 `undefined`，`isVacuousPass()` 就永远放行——门禁的这条防线对它们等于不存在。

四条脚本已各补一行（保留原有中文汇总行不变），现在六条桌面回归都能被门禁正确判定。

### 6.4 索引源冒烟（`smoke:index`）的两个环境假设

2026-11-20 在 rc.5 上补跑 `pnpm smoke:index`，首跑 **5/12 FAIL**。逐项排查后确认**不是宿主变化**
（`@deepseek-ai/dsh-client-ui-plugin-market` 与 `dsh-plugin-market-index` 在 rc.3→rc.5 逐字节相同），
是脚本继承了本机状态、又没等首启弹窗，两个问题叠加成连环红：

1. **临时 profile 继承了真实 profile 的索引源。** 冒烟从 `~/.dsh/profiles/desktop` 复制 profile，而真实
   profile 的 `cordis.patch.yml` 里有 `- id: plugin-market` + `config.indexes`（用户自己加过索引源）。
   继承后「发现页空状态」不成立，「添加索引源」入口消失，替而代之的是「管理索引源」流程；脚本把 URL
   填进了**搜索框**，于是后面「4 个插件/版本/分类」全空。修法：复制后整条删掉 `plugin-market` 行。
2. **首启「预览版说明」比第一次点击晚一拍。** 它盖住发现页，后续点击全部打偏。修法：`dismissNotice()`
   轮询到它真正消失，并加一条断言。

修后 **13/13 PASS**（新增第 2 条断言）。教训：**复制真实 profile 的冒烟，必须显式清掉被复制进来的
用户配置**（索引源、市场源之类）；否则一次「用户自己点过某功能」就会让冒烟变红，看起来像升级坏了。

**同一个「首启说明晚一拍」随后也打到过 `smoke:advisor`**（2026-11-20 11:00 左右：14/14 → 5 项 FAIL，
斜杠菜单空、设置 `no-settings`；复跑仍红，确认与插件/宿主无关）。修法相同：`dismissNotice()` 轮询到弹窗
真正消失并单独断言（14 → 15 项），斜杠菜单断言留一次不降低断言的重试。**凡是「打开页面后只点一次弹窗按钮」
的冒烟脚本，都应该按这个模式改**——它跟着机器负载时快时慢。

### 6.5 门禁护栏：计数行从「约定」变成「机器检查」

[plugin-conventions §6.1](../plugin-conventions.md#61-桌面端自动化测试是硬性要求) 要求桌面脚本收尾打印
`N PASS / M SKIP / K FAIL`，但 2026-11-19 发现只有 btw 打了这一行；`gate.mjs` 的 `parseCounts()` 拿不到
计数时返回 `undefined`，`isVacuousPass()` 于是放行——假绿防线对没打计数行的脚本等于不存在。2026-11-20 补了三层护栏：

1. `gate.mjs` 新增 `desktopGateVerdict()`：`missing-counts`（没有计数行）/ `vacuous`（0 PASS 0 FAIL）/ `ok`，
   前两种都判门禁失败并给出可操作提示；
2. `pnpm check` 静态扫 `scripts/smoke-*-desktop.mjs`，缺计数行直接 error；模板
   `templates/plugin-desktop-smoke/smoke.js` 也带上了这一行（否则新插件天生违规）；
3. 单测锁住三种判定与「模板生成 → 检查通过」「漏计数行 → 报错」。

随后又把「六连 gate」收成一条 `pnpm gate:all`（verify/probe 只跑一次、桌面步骤自动切空闲会话并在结束切回），
并支持 `--repeat 2` 做幂等自检；`--dry-run` 的计划生成抽成纯函数（`scripts/test/gate-all.test.js`），
CI 里跑 `pnpm gate:all --dry-run` 守住六插件脚本结构。

**web 冒烟也补上了计数行（2026-11-20）**：此前只有 btw 打 `N PASS / M SKIP / K FAIL`，其余六条打的是
「PASS 全部 N 项」，`gate:all` 对 web 只看退出码——全 SKIP 的 web 冒烟仍然会绿。现在所有 `smoke-*.mjs`
（`smoke-agent-tool` 例外，它需要凭据、不在门禁里）都打标准计数行，`check-plugins.mjs` 静态拦，
`gate:all` 用 `gateVerdict()` 对 web 与桌面做同一套「缺计数行 / 全 SKIP」判定。
同一轮把 6 份复制粘贴的「首启弹窗轮询」收进 `scripts/lib/browser-helpers.mjs`（`NOTICE_DISMISS_SOURCE`），
并用它修好了 `readme-shots-session-rewind.mjs` 的一个真问题：它复制真实 profile 后没清理用户自带的
第三方 bundle，`dsh plugin add` 会报 `cannot resolve profile bundle`（与索引冒烟同一类环境假设）。

**索引源验收也入库了（2026-11-20）**：`pnpm smoke:index` 支持 `SMOKE_INDEX_URL=<url>` 直接验线上索引
（发版后验 registry → jsDelivr 整条链路），标题与默认版本从当前索引文档派生；本地与线上两种模式各
**13/13**。发版后的例行动作改成一条命令，不再用一次性脚本。

## 7. 下次升级要做什么

1. 升级前跑一次 `pnpm probe:runtime` 留基线，升级后立刻再跑；先分清「能力没了」和「源码形态变了导致匹配不到」。
2. 探针里**任何带哈希的路径**都不要写死；`dist/assets/*` 用 `filePattern` 扫。
3. 想搞清楚「到底变了什么」，直接按 §1.1 对**你依赖的包**做 rc(n) vs rc(n+1) 的 tarball 逐包 diff；带 sourcemap 的 client 包先比 `sourcesContent`，再看字节。
4. 重点看三件事：`SESSION_FORMAT_VERSION`、`sessionPersistence` 是否终于有删除 API、client 半有没有换构建形态；外加新 LLM 失败码（本版是 `CONTENT_REFUSED`）。
5. 冒烟**串行**跑：一条 `pnpm gate:all --repeat 2 --idle-session <空闲会话>` 就把六条 web + 六条桌面（live 版 + CDP 9222）串起来，脚本会在每条桌面回归前切到空闲会话、结束切回原会话，并拦「缺计数行 / 全 SKIP」的假绿；手工跑时同样不要并发，桌面回归之间**先切回会话视图**。
6. 新建 `docs/runtime/<新版本>.md`，更新 AGENTS.md、plugin-conventions、两份根 README 的徽章、各插件兼容表与测试手册（`pnpm check:docs` 会拦）；重跑 `pnpm tokens:host` 并确认快照 `_meta.dshVersion` 跟着变（`--check` 不看 `_meta`，别被「新增 0、移除 0」骗过去）。
7. 冒烟脚本（web 与桌面都算）的收尾行格式不能改；新增脚本时照抄 `N PASS / M SKIP / K FAIL`——`pnpm check` 现在会静态拦所有 `smoke-*.mjs`（`smoke-agent-tool` 例外），不用等下一次升级才发现漏打。

## 8. 宿主侧本地化的两个事实（2026-11-20 实测，btw 0.6.1 排查）

### 8.1 宿主没有 locale 服务：命令文案由插件自己负责

**结论：`ctx.locale` 只存在于 client 半；host 半拿不到任何翻译 API，`commands.register()` 的
`description` / `input.hint` 与命令结果 `{ kind, text }` 全部由宿主逐字透传。** 官方包的
`locale/*.json` 不是可编程字典，宿主只把它当**插件展示元数据**读两种固定字段。

取证（`app.asar` 内随包源码，与 npm `@deepseek-ai/dsh-client-locale@0.2.2-rc.5` 交叉一致）：

- 唯一的 `locale` 服务在 client 半：`@deepseek-ai/dsh-client-locale/src/client/index.ts` 里
  `new LocaleRuntime(...)` → `ctx.provide('locale', ...)`；宿主半的
  `dsh-client-locale/src/index.ts` 只注册 settings，不翻译。全树 `inject: ['locale']` 只出现在
  `*/src/client/*`。
- client 字典契约是**扁平点号键**：`type LocaleDict = Record<string, string>`，
  `register()` 原样 `locales.set(localeKey(locale), entries)`，`lookup()` 只做 `entries[key]`；
  全树没有 `flatten/unflatten/toFlat`，传嵌套对象不会报错、但点号键永远 miss。
- host 的 `@deepseek-ai/dsh-commands/src/index.ts` 只校验 `description` 是非空字符串后冻结；
  `@deepseek-ai/dsh-client-ui-commands/src/client/service.ts` 对插件命令只做
  `{ description: c.description, hint: c.input.hint }` 透传（只有 6 个第一方内置命令走
  `builtinRowFace(c, this.t)` 白名单翻译，第三方插件无法加入），命令结果走
  `noticeFor → notify(level, text)` 也不翻译。
- `@deepseek-ai/dsh-app-boot/src/package-meta.ts` 读插件 `locale/<lang>.json` 时只取
  `meta.title` / `meta.description`（缺省回落 `package.json`），产出 `LocalizedText` 交给浏览器
  的 `ctx.locale.resolveText()`；官方包 2168 个 `locale/*.json` 最大 1012 B，内容全是 `meta`。

**对插件的含义**：host 半要输出什么语言，必须自己决定并自己读自己的文案表；宿主不会因为你把
键写成嵌套/扁平而换一种行为，也不会帮你把 `locale/*.json` 接进命令系统。btw 0.6.0 的
「`/btw` 结果走英文 FALLBACK」就是这个前提 + 加载器只 merge 嵌套对象造成的（见
[testing/btw.md §0.6.1](../testing/btw.md)）。

### 8.2 client 半的 bundle 在宿主进程内按 `rev` 缓存：换文件后刷新页面可能仍跑旧字节

**结论：改完 client 半，光刷新页面不保证加载新代码；最稳的是重启桌面版。**

2026-11-20 实测经过：

1. 把 btw 的新 `lib/client.js` 装进 live `desktop` profile，`Page.reload` 后**新代码生效**
   （界面出现新的转正提示，证明这条路径可行）。
2. 同版本再换一次 `client.js`（只差空格处理），连续多次 `Page.reload`（带
   `Network.setCacheDisabled`、`ignoreCache`，甚至硬导航到 `dsh-app://app/?_r=...` 再回来），
   **运行时行为一直是旧版本**；同期用 `Network.enable` 抓到的 `dsh-app://app/plugins/??<pkg>/client.js&rev=…`
   响应正文里已经是新代码。
3. `window.__DSH_BOOT__.entries[].rev` 在多次刷新/换版本（含把包版本 0.6.0 改成 0.6.1 重装）后
   仍是同一个值；`dsh-app://app/` 硬导航会丢会话上下文（要靠普通刷新恢复）——不要用这种方式
   做「刷新」。

结合 [rc.3 §6.1](0.2.2-rc.3.md#61-核对页面到底加载了哪一版-client-半2026-11-14) 的结论
（`rev` 不是内容哈希，同一 `rev` 下曾下发过至少三份不同内容），可以判定：**宿主在进程内缓存了
按 `rev` 分组的 client bundle**，刷新只重建渲染进程、不会让宿主重新打包。因此：

- 验证 client 半改动：**重启桌面版**（host 半改动本来就需要重启，两者一致）；
- 只想确认「页面到底跑了哪一版」：用 `Network.getResponseBody` 抓
  `plugins/??<pkg>/client.js&rev=…` 的正文做特征检查（btw 0.6.1 就是这样确认旧 bundle 的）；
- 不要在自动化里指望「换文件 + 刷新」一定生效——会得出「修复没生效」的错误结论。

**2026-11-20 重启桌面版后复验通过**：btw 的 boot `rev` 从 `c349aec56fdb` 变成 `ca05b9ee487f`；
用 CDP `Debugger.getScriptSource` 抓「已执行」的 `plugins/??…` 模块，里面已是最终代码标记；
同一会话的 `/btw` 结果文案也从英文 FALLBACK 变成中文（斜杠菜单描述 `不打断主任务地提一个只读旁问`）。
所以这条结论的实操版本就是：**改完 client 半，重启桌面版一次再验**。

## 9. subagent provider：`spawn`（fresh）与 `fork` 并存（2026-11-20 实测）

base 组合同时挂载两个进程内 provider（`@deepseek-ai/dsh-base/cordis.patch.yml`）：

- `subagent-spawn-in-process` → provider 名 **`spawn`**，`inheritsParentContext: false`；
- `subagent-fork-in-process` → provider 名 **`fork`**，`inheritsParentContext: true`。

`ctx.subagents.getProvider(name)` 可拿到 provider 对象（含 `inheritsParentContext` 与
`capabilities: {agentOptions, agentPreset, outputSchema, depthLimit}`；spawn 的 `agentPreset` 为 true，
fork 为 false）。`startActivation({ provider:"spawn", parent, prompt: ContentBlock[], delivery:"caller" })`
在**插件命令上下文**里可用：调用方给的两段 text 材料会被模型读到；子代理不再携带父会话上下文
（实测父会话 `contextPressure ≈ 668K`，spawn 子代理 usage 仅 ~20K tokens）；在子代理 ctx 上挂
`ctx.tools.guard(...)` 也可用（返回 disposer）。

限制：spawn 子代理结果 settle 后 `ctx.sessions.get(childId)` 已拿不到事件（会话被拆掉），
需要在 `startActivation` 返回后**立刻**用 childId（btw 的 `onChild` 就是这个时点）做流式/归档；


### 9.1 spawn 的固定开销构成：preset 选择、MCP 工具 schema

spawn 子代理的 prompt = 所选 preset 的组成 + **宿主级工具 schema**（含根
`~/.dsh/cordis.patch.yml` 里挂的 MCP 工具）。`agentPreset` 能换 preset（`agentPresets.list()`
实测有 `standard` / `ptc` / `minimal` / `cordis`），但**动不了宿主级 MCP 工具**。2026-11-20 实测
（同一真实会话、`prompt` 只有一句 "Reply with exactly: OK"）：

| 宿主                                       | 默认（父级 generation） | `agentPreset:"minimal"` |
| ------------------------------------------ | ----------------------- | ----------------------- |
| 精简 profile（临时宿主）                   | 20,257 tokens           | **6,019** tokens        |
| 完整 profile、无根 MCP 配置                | 31,550 tokens           | —                       |
| 完整 profile + 根 MCP（rea，本机真实配置） | —                       | **100,526** tokens      |
| live 桌面 bounded（standard + digest）     | 118,730 tokens          | —                       |

结论：固定开销的大头是**宿主级工具 schema**（本机 rea MCP 约 87K tokens），换 `minimal` 只省
~15%；`tools.guard` 只拦执行、不减少 schema，`SubagentStartRequest` 也没有工具过滤字段。因此
「用轻 preset 压低子代理成本」不成立；要显著降本需要上游提供 tool scoping / tool-free child。
调用方别漏根 `cordis.patch.yml` 做开销评测，否则会测出偏低的假值。

### 8.3 `gh` 的两个行为坑（2026-11-21 真机 e2e 抓到）

在真实仓库上跑「开 PR → 合并」时踩到、并直接导致过一次**假成功**：

1. **`gh pr merge <n>` 不带 `--repo` 时，按「进程当前目录所在的 git 仓库」解析目标。**
   插件在宿主进程里跑命令，cwd 不是项目目录，于是 `gh pr merge 1 --squash` 打到了
   **另一个仓库**（本仓库）的 PR #1。
2. **对已经合并/关闭的 PR，`gh pr merge` 仍可能返回 exit 0**（"already merged"），
   所以「退出码 0 = 合并成功」这个判据不成立。上面那次假成功正是这两条叠加。

同一轮还确认了 GitHub 的两个异步行为：

- **PR 刚创建后 `mergeable` 可能是 `UNKNOWN`**（服务端还在算），通常 1–3 秒后变 `MERGEABLE`。
  把 `UNKNOWN` 当作「不可合并」硬拒会误杀正常流程；正确做法是有界重试。
- **draft PR 不能合并**（`gh pr merge` 会被拒），所以「开 draft PR + 自动合并」这条组合
  必须在合并前先判 `isDraft`，而不是等 GitHub 报错。

**对插件的结论**：危险动作执行前必须 (a) 显式解析目标仓库并传给 `--repo`，
(b) 用 `gh pr view --json isDraft,mergeable,state` 做前置校验，(c) 不能以退出码作为唯一成功判据。
