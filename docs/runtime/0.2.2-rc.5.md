```bash
mkdir -p /tmp/dshdiff && cd /tmp/dshdiff
for p in dsh-session dsh-tools dsh-client-ui-chat …; do
  npm pack "@deepseek-ai/$p@0.2.2-rc.3" --silent >/dev/null
  npm pack "@deepseek-ai/$p@0.2.2-rc.5" --silent >/dev/null
```

### 5.1 桌面回归的两个视图前置（本轮都踩到了）

桌面回归驱动的是**正在运行的那个桌面版**，脚本读的是「当前可见会话」。agent 在自己的会话里跑回归时，有两个前置必须自己先摆好：

1. **可见会话不能是「正在跑回合」的会话。** 否则 advisor 脚本按设计不敲键盘：`FAIL 当前会话空闲（没有正在跑的回合）` + 13 条 SKIP。做法：先把可见会话切到一个**空闲会话**再跑（切换只是换视图，不会中断正在跑的回合，[rc.3 §6](0.2.2-rc.3.md#6-本机实测2026-11-14) 已实测）。
2. **上一条桌面回归不能把页面留在别的页面。** casefile 的桌面回归结束时按了 Esc（断言「页面仍可用」），但**不会离开「案卷」主面板**；紧接着跑 btw 会因为没有 composer 而报 `FAIL 输入框左侧出现 btw 按钮`（本轮首发就是这个假红，重跑前先切回会话即 18 PASS / 1 SKIP）。串行跑多条桌面回归时，**两条之间先点回任一会话**。

这两条都不是 rc.5 的破坏性变化，是「谁在跑回归」的环境问题——写进了 §7 的升级清单。

### 5.2 命令卡片只在**非空白会话**里渲染（2026-11-20 实测）

排查 `smoke:btw --deep` 的两条 SKIP（「回车后聊天流出现节点」「提交 /btw 后出现命令卡片」）时确认的宿主行为：**在全新（blank）会话里提交一条不产生回合的斜杠命令，命令会在宿主执行、结果落进会话日志与插件数据，但客户端一个 `[data-chat-flow-kind]` 节点都不会渲染。**

证据链：

1. **命令确实执行了。** 临时 `DSH_HOME` 的会话日志里有 `command/run` → `command/done`（`kind:"success"`，`text:"OK\n\n— btw · new 1.5K tokens · cached 9.2K · 1.5s"`），插件 history 也有 `status=done` 的记录；同一条会话里**没有** `turn/start` / `user/message`（命令是 log-only 追加，不包回合）。
2. **页面停在 hero 空态。** 提交前后 `body` 长度都是 ~130 字符、`[data-chat-flow-kind]` 数量为 0；`data-phase` 是 `hero`。整页刷新、手动点侧栏那一行「新会话」也一样。
3. **发一条普通消息就全好了。** 在同一会话里发一句 `hi`（一次真实的模型回合）后：`data-phase` 变 `active`，**之前那 3 条命令卡片一次性回溯出现**（两条 `--deep` 的 `/btw` + 一条无参 `/btw`），随后新提交的 `/btw` 立即渲染成第 4 张卡片。

客户端源码对得上（`@deepseek-ai/dsh-client-ui-conversation` 的 sourcemap 里有原始 TS）：

- `contract/snapshot.ts` 的 `conversationPhase()`：`active` 只在「有 activeTargets / 会话不 blank 且不在等首回合 / 正在跑回合」时成立，否则是 `blank` / `engaging`；
- `skeleton/ConversationMainPanel.tsx`：`shellPhase === 'blank'`（且会话已 open 或列表摘要 blank）就直接走 hero，**不渲染 `conversation.session` 的 views**，所以命令节点连构建机会都没有。

**结论与用法：**

- 这是**通用宿主行为**，与 btw 插件无关（命令卡片由宿主的 `conversation-nodes/command.ts` 统一构建；`recordInput: false` 只影响 `command/run.args` 是否记录，不影响渲染）。
- 想在自动化里断言「命令卡片」，会话必须**先 materialize**（至少一个真实回合）；否则断言必然空转。`smoke:btw --deep` 已改成先发一句 `hi` 热身再提交，两条 SKIP 变成真实 PASS（30 PASS / 1 SKIP / 0 FAIL）。
- 反过来，插件**不能假定**自己的 `/命令` 输出在空白会话里可见：用户在新会话里敲 `/btw` 只会看到「什么都没发生」（输出只在会话日志 / 插件面板里）。插件若需要可见回执，只能靠自己的 UI 面（btw 的右侧栏就是这个形态）。

`pnpm smoke:session-delete-desktop --require` 在回收站**为空**时报：

```
FAIL 回收站面板保留全选与批量操作 :: {"hasTabs":false,"hasBatch":false,"text":"会话回收站回收站是空的。关闭"}
```

**根因在脚本，不在插件**：插件的回收站面板在 `entries.length === 0` 时只渲染空态（「回收站是空的。」），工具条（全选 / 恢复（n）/彻底删除）与条目行都在 `entries.length > 0` 分支里。断言把「有空条目时才存在的东西」写成了无条件断言，于是回收站空时必红；「条目：标题可读」那条更糟——`rows === 0` 被写成通过，等于**什么都没验证还报绿**。

修法（只改脚本）：用面板里的 `.dsh-sdel-row` 数量判断空/非空，空时两条记 **SKIP** 并给出原因，非空时断言不变（更严格，去掉了 `rows === 0` 的假通过）。修后实测 **16 PASS / 2 SKIP / 0 FAIL**（`pnpm gate session-delete` 不再假红）。

### 6.2 四条桌面脚本补打印门禁依赖的计数行

[plugin-conventions §6.1](../plugin-conventions.md#61-桌面端自动化测试是硬性要求) 要求桌面脚本收尾打印 `N PASS / M SKIP / K FAIL`，`scripts/gate.mjs` 的 `parseCounts()` 靠它识别「跑过但一条断言都没执行」的假绿。本轮实测：**只有 `smoke-btw-desktop` 打了这一行**；advisor / next-step / session-rewind / casefile、以及**本轮修好的** session-delete 都没有打，`parseCounts()` 返回 `undefined`，`isVacuousPass()` 就永远放行——门禁的这条防线对它们等于不存在。

四条脚本已各补一行（保留原有中文汇总行不变），现在六条桌面回归都能被门禁正确判定。

### 6.4 索引源冒烟（`smoke:index`）的两个环境假设

2026-11-20 在 rc.5 上补跑 `pnpm smoke:index`，首跑 **5/12 FAIL**。逐项排查后确认**不是宿主变化**

2. **首启「预览版说明」比第一次点击晚一拍。** 它盖住发现页，后续点击全部打偏。修法：`dismissNotice()`
   轮询到它真正消失，并加一条断言。

修后 **13/13 PASS**（新增第 2 条断言）。教训：**复制真实 profile 的冒烟，必须显式清掉被复制进来的
用户配置**（索引源、市场源之类）；否则一次「用户自己点过某功能」就会让冒烟变红，看起来像升级坏了。

**同一个「首启说明晚一拍」随后也打到过 `smoke:advisor`**（2026-11-20 11:00 左右：14/14 → 5 项 FAIL，

### 6.5 门禁护栏：计数行从「约定」变成「机器检查」

## 8. 宿主侧本地化的两个事实（2026-11-20 实测，btw 0.6.1 排查）

### 8.1 宿主没有 locale 服务：命令文案由插件自己负责

**结论：`ctx.locale` 只存在于 client 半；host 半拿不到任何翻译 API，`commands.register()` 的
`description` / `input.hint` 与命令结果 `{ kind, text }` 全部由宿主逐字透传。** 官方包的
`locale/*.json` 不是可编程字典，宿主只把它当**插件展示元数据**读两种固定字段。

取证（`app.asar` 内随包源码，与 npm `@deepseek-ai/dsh-client-locale@0.2.2-rc.5` 交叉一致）：

- 唯一的 `locale` 服务在 client 半：`@deepseek-ai/dsh-client-locale/src/client/index.ts` 里
  `new LocaleRuntime(...)` → `ctx.provide('locale', ...)`；宿主半的
  `dsh-client-locale/src/index.ts` 只注册 settings，不翻译。全树 `inject: ['locale']` 只出现在
  `*/src/client/*`。
- client 字典契约是**扁平点号键**：`type LocaleDict = Record<string, string>`，
  `register()` 原样 `locales.set(localeKey(locale), entries)`，`lookup()` 只做 `entries[key]`；
  全树没有 `flatten/unflatten/toFlat`，传嵌套对象不会报错、但点号键永远 miss。
- host 的 `@deepseek-ai/dsh-commands/src/index.ts` 只校验 `description` 是非空字符串后冻结；
  `@deepseek-ai/dsh-client-ui-commands/src/client/service.ts` 对插件命令只做
  `{ description: c.description, hint: c.input.hint }` 透传（只有 6 个第一方内置命令走
  `builtinRowFace(c, this.t)` 白名单翻译，第三方插件无法加入），命令结果走
  `noticeFor → notify(level, text)` 也不翻译。
- `@deepseek-ai/dsh-app-boot/src/package-meta.ts` 读插件 `locale/<lang>.json` 时只取
  `meta.title` / `meta.description`（缺省回落 `package.json`），产出 `LocalizedText` 交给浏览器
  的 `ctx.locale.resolveText()`；官方包 2168 个 `locale/*.json` 最大 1012 B，内容全是 `meta`。

**对插件的含义**：host 半要输出什么语言，必须自己决定并自己读自己的文案表；宿主不会因为你把
键写成嵌套/扁平而换一种行为，也不会帮你把 `locale/*.json` 接进命令系统。btw 0.6.0 的
「`/btw` 结果走英文 FALLBACK」就是这个前提 + 加载器只 merge 嵌套对象造成的（见
[testing/btw.md §0.6.1](../testing/btw.md)）。

### 8.2 client 半的 bundle 在宿主进程内按 `rev` 缓存：换文件后刷新页面可能仍跑旧字节

**结论：改完 client 半，光刷新页面不保证加载新代码；最稳的是重启桌面版。**

2026-11-20 实测经过：

1. 把 btw 的新 `lib/client.js` 装进 live `desktop` profile，`Page.reload` 后**新代码生效**
   （界面出现新的转正提示，证明这条路径可行）。
2. 同版本再换一次 `client.js`（只差空格处理），连续多次 `Page.reload`（带
   `Network.setCacheDisabled`、`ignoreCache`，甚至硬导航到 `dsh-app://app/?_r=...` 再回来），
   **运行时行为一直是旧版本**；同期用 `Network.enable` 抓到的 `dsh-app://app/plugins/??<pkg>/client.js&rev=…`
   响应正文里已经是新代码。
3. `window.__DSH_BOOT__.entries[].rev` 在多次刷新/换版本（含把包版本 0.6.0 改成 0.6.1 重装）后
   仍是同一个值；`dsh-app://app/` 硬导航会丢会话上下文（要靠普通刷新恢复）——不要用这种方式
   做「刷新」。

结合 [rc.3 §6.1](0.2.2-rc.3.md#61-核对页面到底加载了哪一版-client-半2026-11-14) 的结论
（`rev` 不是内容哈希，同一 `rev` 下曾下发过至少三份不同内容），可以判定：**宿主在进程内缓存了
按 `rev` 分组的 client bundle**，刷新只重建渲染进程、不会让宿主重新打包。因此：

- 验证 client 半改动：**重启桌面版**（host 半改动本来就需要重启，两者一致）；
- 只想确认「页面到底跑了哪一版」：用 `Network.getResponseBody` 抓
  `plugins/??<pkg>/client.js&rev=…` 的正文做特征检查（btw 0.6.1 就是这样确认旧 bundle 的）；
- 不要在自动化里指望「换文件 + 刷新」一定生效——会得出「修复没生效」的错误结论。

**2026-11-20 重启桌面版后复验通过**：btw 的 boot `rev` 从 `c349aec56fdb` 变成 `ca05b9ee487f`；
用 CDP `Debugger.getScriptSource` 抓「已执行」的 `plugins/??…` 模块，里面已是最终代码标记；
同一会话的 `/btw` 结果文案也从英文 FALLBACK 变成中文（斜杠菜单描述 `不打断主任务地提一个只读旁问`）。
所以这条结论的实操版本就是：**改完 client 半，重启桌面版一次再验**。

## 9. subagent provider：`spawn`（fresh）与 `fork` 并存（2026-11-20 实测）

base 组合同时挂载两个进程内 provider（`@deepseek-ai/dsh-base/cordis.patch.yml`）：

- `subagent-spawn-in-process` → provider 名 **`spawn`**，`inheritsParentContext: false`；
- `subagent-fork-in-process` → provider 名 **`fork`**，`inheritsParentContext: true`。

`ctx.subagents.getProvider(name)` 可拿到 provider 对象（含 `inheritsParentContext` 与
`capabilities: {agentOptions, agentPreset, outputSchema, depthLimit}`；spawn 的 `agentPreset` 为 true，
fork 为 false）。`startActivation({ provider:"spawn", parent, prompt: ContentBlock[], delivery:"caller" })`
在**插件命令上下文**里可用：调用方给的两段 text 材料会被模型读到；子代理不再携带父会话上下文
（实测父会话 `contextPressure ≈ 668K`，spawn 子代理 usage 仅 ~20K tokens）；在子代理 ctx 上挂
`ctx.tools.guard(...)` 也可用（返回 disposer）。

限制：spawn 子代理结果 settle 后 `ctx.sessions.get(childId)` 已拿不到事件（会话被拆掉），
需要在 `startActivation` 返回后**立刻**用 childId（btw 的 `onChild` 就是这个时点）做流式/归档；


### 9.1 spawn 的固定开销构成：preset 选择、MCP 工具 schema

spawn 子代理的 prompt = 所选 preset 的组成 + **宿主级工具 schema**（含根
`~/.dsh/cordis.patch.yml` 里挂的 MCP 工具）。`agentPreset` 能换 preset（`agentPresets.list()`
实测有 `standard` / `ptc` / `minimal` / `cordis`），但**动不了宿主级 MCP 工具**。2026-11-20 实测
（同一真实会话、`prompt` 只有一句 "Reply with exactly: OK"）：

| 宿主                                       | 默认（父级 generation） | `agentPreset:"minimal"` |
| ------------------------------------------ | ----------------------- | ----------------------- |
| 精简 profile（临时宿主）                   | 20,257 tokens           | **6,019** tokens        |
| 完整 profile、无根 MCP 配置                | 31,550 tokens           | —                       |
| 完整 profile + 根 MCP（rea，本机真实配置） | —                       | **100,526** tokens      |
| live 桌面 bounded（standard + digest）     | 118,730 tokens          | —                       |

结论：固定开销的大头是**宿主级工具 schema**（本机 rea MCP 约 87K tokens），换 `minimal` 只省
~15%；`tools.guard` 只拦执行、不减少 schema，`SubagentStartRequest` 也没有工具过滤字段。因此
「用轻 preset 压低子代理成本」不成立；要显著降本需要上游提供 tool scoping / tool-free child。
调用方别漏根 `cordis.patch.yml` 做开销评测，否则会测出偏低的假值。

### 8.3 `gh` 的两个行为坑（2026-11-21 真机 e2e 抓到）

在真实仓库上跑「开 PR → 合并」时踩到、并直接导致过一次**假成功**：

1. **`gh pr merge <n>` 不带 `--repo` 时，按「进程当前目录所在的 git 仓库」解析目标。**
   插件在宿主进程里跑命令，cwd 不是项目目录，于是 `gh pr merge 1 --squash` 打到了
   **另一个仓库**（本仓库）的 PR #1。
2. **对已经合并/关闭的 PR，`gh pr merge` 仍可能返回 exit 0**（"already merged"），
   所以「退出码 0 = 合并成功」这个判据不成立。上面那次假成功正是这两条叠加。

同一轮还确认了 GitHub 的两个异步行为：

- **PR 刚创建后 `mergeable` 可能是 `UNKNOWN`**（服务端还在算），通常 1–3 秒后变 `MERGEABLE`。
  把 `UNKNOWN` 当作「不可合并」硬拒会误杀正常流程；正确做法是有界重试。
- **draft PR 不能合并**（`gh pr merge` 会被拒），所以「开 draft PR + 自动合并」这条组合
  必须在合并前先判 `isDraft`，而不是等 GitHub 报错。

**对插件的结论**：危险动作执行前必须 (a) 显式解析目标仓库并传给 `--repo`，
(b) 用 `gh pr view --json isDraft,mergeable,state` 做前置校验，(c) 不能以退出码作为唯一成功判据。

---

> **以下 §10–§21 来自 2026-11-23 的六路深度探针**（会话 / 权限 / 文件 / 调度 / UI / 外部），方法都是「`cordis_inspect_query` 读契约 + 临时 `DSH_HOME` 真起宿主 + 一次性探针插件真调用 + 真实 HTTP RPC / 真实浏览器」，没有碰 live profile 的用户数据。证据等级逐条标注：**【实测】**＝真宿主里真调用或真 RPC / 真浏览器渲染；**【静态】**＝随包源码、随包 README、静态 slot catalog（`slot-catalog.ts`）里的契约。只读到契约、本轮没做写验证、或两条证据互相矛盾的，一律在各节末尾的 **unknown** 里明说，**不冒充已验证**。探针出处写 `文件.md §…`，原件是同目录下的 `*.md` 与 `*.jsonl` 原始记录。

**注意点**

- **`create` 不收 model**：只有 `workspaceId / cwd / sessionId / agentPreset` 四个字段；每线程模型必须 create 之后 `selectModel`。`create` 本轮不带 signal 也能成功。【实测】
- **`selectModel` 要有可路由 provider**：无凭据部署 `groups: []`、`routableProviders: []`，此时 `selectModel` 抛 `RemoteError: Select an available model before sending a message`。要验通必须先 `llm.registerAdapter([...], adapter)` 注册一个假 provider（探针就是这么做的）。【实测】
- **`modelCatalog.default` 不等于可用**：它在 `groups` 为空时依然有值（本机是 `{ provider: 'zhinao', model: 'deepseek/deepseek-v4.1-flash', reasoningEffort: 'max' }`）。UI 的模型下拉必须渲染 `groups`，不能拿 `default` 当选项。【实测】
- **`reasoning.efforts` 是部署/模型给的枚举**：本机默认档给的是 `reasoningEffort: 'max'`，所以不要写死 `low/medium/high` 三档，按 `efforts` 渲染、`defaultEffort` 兜底。【实测】
- **queue / steer 是两种不同动作**：`prompt({mode:'queue'})` 落进 `queue[].placement:'queued'`；`updateQueue({action:{kind:'steer'}})` 把同一条改成 `'steering'`；`prompt({mode:'steer'})` 直接以 steering 落队。steer 只保证进队，**不保证被模型采纳**。`queue` 在空闲且无排队时是 `[]`（不是 `null`）。【实测】
- **`cancel` 是异步的，且不会清队列**：`cancel()` 立刻返回 `{ accepted: true }`，但 `state().running` 还是 `true`；约 **1.2 s 后**才变 `false`，而队列里两条 steering **仍在**——「停 turn 不清 inbox」。要确认停了就轮询 `state()`，别拿返回值当已停止。【实测】
- **`state` / `projections` 必须传 signal**：漏了第二次参数会抛 `TypeError: Cannot read properties of undefined (reading 'throwIfAborted')`（`projections` 报的是 `reading 'aborted'`）。TypeScript 里 signal 是必填，运行时不兜底。【实测】
- **行摘要 ≠ 全量投影**：`list()` 的行是 19 键 hints，`sessionStats` / `turnOutline` / `contextPressure` / `contextBreakdown` / `todos` / `actionCards` 都不在里面；步进、上下文压力只能走 `sessionProjections.snapshot()` 或 client 面 `sessionController.control` 流。【实测】
- **「等你」的官方法**是 `state().pendingInput.length > 0`（宿主自己的 `wait()` 就用它判），`wait()` 返回 `reason: 'input-required'` 并带上同一个 `state`。`userQuestions` 投影**不会**跟着变，别拿它判。本轮只实测到 `'question'`，`'approval'` / `'other'` 只到契约层。【实测 + 静态】

**验证方式**：临时 `DSH_HOME`（profile 从 desktop 复制、只留 `@deepseek-ai/*` bundle）+ 探针插件直调；再用真 HTTP RPC（`token → cookie → POST /api/session/<method>`）把 `create / selectModel / state / rename / cancel / archive` 复跑一遍；最后**重启同一个宿主**验 resume 与投影持久化。冷会话 `prompt` 会隐式 resume（`state` 从 `{active:false,running:false,queue:null}` 变成 `{active:true,running:true}`）。探针出处：`session.md §1`（F9/F11/F13/F19/F24/F42/F44）、`§3.1–3.2`、`§4`，原始记录 `session.jsonl` / `session.round1.jsonl`；`wait()` 的返回形状另见 `sched.md §1`（F31）。

**unknown**：`create({ workspaceId })` 与 `create({ sessionId })`（复用命名空会话）本轮没单独实测，只有契约；`prompt` 不带 signal 是否可省未验证（探针两轮都带了）。

## 11. 会话事件 `todo/write` 与 `todos` 投影

**结论：`todo/write` 是宿主级会话事件，todo 清单不用自己维护。** 形状 `{ type: 'todo/write', data: { todos: [{ content, status }] } }`，`status ∈ 'pending' | 'in_progress' | 'completed'`；整表快照、last-wins、log-only（不是派生历史）。【实测】

- 订阅：`ctx.on('session/event', (session, event) => { if (event.type === 'todo/write') … })`——运行时按字符串过滤，插件拿不到它的 TS 类型。【实测】
- 写：`agent.session.append('todo/write', { todos: [...] })` 返回 `{ seq }`，同一条会同时出现在 `session/event` 和 `projections().values.todos` 里。【实测】
- 折进投影：`values.todos`（`SessionProjectionMap.todos`，summary-excluded，只在全量投影里，不在 `list()` 行 hints 中）。【实测】
- **它不在 `dsh-session` 的 `SessionEventMap` 本体**里：由 `@deepseek-ai/dsh-tool-todo` 的 `declare module '@deepseek-ai/dsh-session/types'` 合并声明，生成的 `KNOWN_SESSION_EVENT_TYPES` 里含它。所以插件里按**字符串常量**处理（`event.type === 'todo/write'`），别指望它出现在 `@deepseek-ai/dsh-session` 的类型里；插件自己也别 `append` 这条事件（会污染日志、与宿主的清单打架）。【静态】

## 12. 权限：`permissionPresets` / `approval` / `sandbox`+`sandboxPolicy`

这是本轮信息量最大的一节，因为**本部署的默认档是「全开 + 从不问」**，跟「默认关、提示打开自动模式」的直觉正好相反。

```ts
// 一个 preset 就是两个旋钮的组合
PresetSpec = { sandbox: 'read-only' | 'workspace-write' | 'danger-full-access',
               approval: 'ask' | 'never' }        // 【静态】dsh-permission-presets/src/index.ts:58-67

permissionPresets: {
  catalog(): { options: {value,name}[], defaultOptions: {value,name}[], defaultPreset: string }
  resolve(name): PresetSpec
  current(session): string
  set(session, name): void                  // 追加 permission/preset + 逐 knob 走 setSandboxMode/setApprovalPolicy
  registerAuto(admit): Disposable           // 唯一运行时注册槽位
}
approval: {
  setPolicy(agent, 'ask' | 'never'): void   // 收 Agent，会 agent.inject 一条 user 消息
  overrideOf(session): 'ask' | 'never'
  request({ agent, toolName, reason, signal? }): ApprovalOutcome   // signal 在入参对象里，不是第二个位置参数
}
sandbox:       { confine(argv, policy, signal): { argv, enforcement, denialSignatures, runnerFailureRules } }
sandboxPolicy: { defaultMode, workspaceRoot, additionalWritableRoots,
                 resolve({ session, mode? }), registerWritableRoot(session, dir), overrideOf(session) }
ApprovalOutcome = 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

注意 **Session 与 Agent 不是同一个入参**：`permissionPresets.set/current`、`sandboxPolicy.resolve/overrideOf/registerWritableRoot` 收 **Session**（`agent.session`，或 `sessions.create(...)` 出来的 Session）；`approval.setPolicy` / `approval.request` 收 **Agent**。

**三条硬事实（都做了写验证）**

1. **preset 名字是部署配置，插件不能注册新的、也不能写死。** `static Config.presets` 是 `z.dict`（`custom` / `auto` 是保留名，构造期就抛）；唯一运行时注册入口 `registerAuto` **本部署已被 `@deepseek-ai/dsh-experimental-auto-review` 占用**——直接调报 `permission: preset "auto" is already registered`。正确写法是 `catalog().options` → 逐个 `resolve(name)` → 按 `PresetSpec` 的 bundle 挑（最宽 = `sandbox==='danger-full-access' && approval==='never'`；最窄 = `sandbox==='read-only'`），挑不到就不要硬切。【实测】
2. **本部署 `defaultPreset` 已是 `danger-full-access`（sandbox 全开 + `approval: never`）**，每个新 agent 创建即得（`permission/preset=danger-full-access`、`approval=never`）。所以「项目级自动模式开关」实际上是**收窄**（切回 `read-only` / `workspace-write`），文案别写反。`catalog()` 原文：4 个 option（`read-only` / `workspace-write` / `danger-full-access` / `auto`）、3 个 `defaultOptions`（不含 `auto`）。其中 `read-only` 这一档**不在官方默认表里**，是本机 profile 的 patch 加的——又一个「名字不能写死」的理由。【实测】
3. **`set()` 只写日志，不注入模型可见提示**：它追加 `permission/preset` 再逐 knob 写，enforcement 因为读投影所以**立即生效**（活着的 agent 上切、空闲会话里切都验证过）；但「模型马上知道」是 `/permission` 命令那条路径（内部 `approval.setPolicy` 会 `agent.inject`）干的，我们没有那个句柄。【实测】

**审批（`approval`）的四个坑**

- **只有「这一次」**：`ApprovalOutcome` 的唯一授予值是 `allowed-once`，宿主没有通用的「记住这个授权」。唯一现成的「始终允许」是 CUA 原生应用授权（落它自己的 store）。想「设为默认目录」只能落**我们自己的** store。【静态 + 实测】
- **禁止在插件里裸调 `approval.request`**：① 空闲（没有 open turn）时直接抛 `approval.request() outside an open turn…`（它要求 `approval/asked` + `approval/decided` 成对且被 turn 包住）；② `ask` 策略下若没有浏览器客户端应答，会**一直挂着**（本轮探针用 6 s 上限，结果是 `TIMEOUT`——具体能挂多久 **unknown**）；③ `never` 策略在 waterfall **之前**就短路成 `rejected`，任何 listener 都拦不住。【实测】
- **正确姿势**：要问用户就走 `tools/pre-execute` 返回 `{ kind: 'ask' }`（`dsh-tools` 的 `serviceAsk` 会去调 `approval.request`），或直接用 `userQuestions.ask`。三键授权卡的 `intent` 校验是硬的：`{ kind:'approval', approve, reject, always? }` 里三个 label 必须都在 `options` 里，否则当场 `BAD_INTENT`。【静态 + 实测】
- **没有匹配 preset 时的兜底**：`session.append('approval/policy', { policy:'never' })` + `session.append('sandbox/mode', { mode:'danger-full-access' })`——`overrideOf` / `resolve` / `current` 都读回正确。只用公开 `Session` API、不引 `@deepseek-ai/*` 依赖，但**吃版本风险**（事件类型带版本，见硬性约定 1）。【实测】

**`sandbox` 只能配本地文件效果**：`confine()` 返回的是 macOS Seatbelt 包一层（`argv: ['sandbox-exec','-p',…]`、`enforcement:'full'`、`denialSignatures:['operation not permitted']`）；`SandboxMode` 词汇明确写「Network and process visibility are outside this vocabulary」。**没有**域名白名单、env 注入、网络开关、云端 region 之类的旋钮；宿主也没有任何 remote/cloud/microVM 沙箱实现。【静态 + 实测】

**部署级默认**：`settings.update('permission', { defaultPreset })` 是 `applies:'live'`，改完新 agent 的初始 preset 跟着变——这是我们能碰的「全局默认」，但**不是项目级**。【实测】

**验证方式**：临时宿主 + 探针插件逐项写验证（`catalog` / `resolve`×4 / `set`+`current` 双向 / 幂等 / 未知名字抛错 / 活 agent 立即生效 / `setPolicy` / `request` 四种情形 / `registerWritableRoot` 的 dispose / `settings.update`），另有 live desktop 只读契约对照。探针出处：`perm.md §2`（catalog 原文与四条硬事实）、`§2.3`、`§3`、`§5`、`§7.1`、`§8`，原始记录 `perm.jsonl`（`2.catalog`、`11c/11f/12/18a`、`13b/13c`、`16a/16b`、`19b`、`20b/20c`）。

**unknown**：`approval.request` 无应答时到底能挂多久——原始探针用 6 s 上限，只得到 `TIMEOUT` 就放弃了（另有汇总口径写 149 s，但两者不能互证，这里按 unknown 记）；`registerAuto` 若槽位空出来是否真能用（本部署已被占用，未验证）。

## 13. `workspaceFiles`：会话作用域的文件面

**结论：文件「列 / 读 / stat / 流式变更」宿主全给，`search` 只搜名字、不搜正文，全文搜索得自建。**

```ts
WorkspaceFileScope = { sessionId, workspaceRoot }

list(scope, path, signal)                        → { path, entries[], truncated }      // 限 workspaceRoot 内
read(scope, path, { offset, limit }, signal)      → { offset, lines, eof, text }        // offset 是 1 起始
stat(scope, path, signal)                         → 单条 stat
readBytes(scope, path, { range:{ offset, length } }, signal)
search(scope, { query, excludedPaths, includeHidden, respectGitignore }, signal)
                                                  → { matches: [{ path, type }] }        // 只匹配名称与路径
changes(scope, path, signal)                      → AsyncIterable，首帧 { kind:'ready' }
```

契约默认值（`workspaceFiles.config`，【实测】读回）：`maxBytes: 2097152`、`maxFileBytes: 33554432`、`maxLines: 5000`、`maxEntries: 2000`；搜索 `maxResults: 512`、`maxEntries: 100000`、`timeoutMs: 30000`。超限是**静默截断**（`truncated: true`），不是报错。

**注意点**

- **`list` 与 `read` 的作用域不对称**：`list` 被 `confine` 限制在 `workspaceRoot` 内，越界报 `workspace-file/outside-workspace`；`read` **明确允许 root 之外**（可以拿来预览收藏的外部文件）。`changes` 越界报 `Directory is outside the workspace`。【实测】
- **多目录 = 多 workspaceRoot**：宿主的数据模型是「一个目录一个 Workspace」（`Workspace.path` 单值），**没有**「一个项目多目录」。要浏览第二个目录只有两条路：`workspaceRegistry.create(dir2)`（= 多一个 workspace，不是给项目加目录），或换 `scope.workspaceRoot` 再调。≤10 个目录不需要碰任何宿主上限。【实测】
- **不要用 `workingDirectory.set` 在同一会话里来回切目录**：它会顺带换掉该会话的 `workspaceFiles` root，也会改写 AGENTS.md 的发现链（`working-directory/change` 还会写进模型可见的会话日志）。【实测】
- **client 半的 wire 只传 sessionId**：`rpc.call('/api', 'workspaceFiles/list', { workspaceFileScopeId: sessionId, path })`，root 由会话 `header.cwd` 派生。【实测】
- 要自建的三块：全文搜索（宿主只搜文件名/路径）、provenance（`workspaceChanges.summary(sessionId, seq)` 只覆盖 live 会话、只到 turn 粒度）、计量（`storage` / `storageDomain` 是 KV 设施，没有大小 API）。【实测 + 静态】

**验证方式**：临时宿主 + 探针插件，`list`（root / 绝对路径 / 子目录 / 第二个 root / 越界期望拒绝）、`read`（普通 / 带 offset+limit / 跨 root）、`stat`、`readBytes`（range）、`changes`（首帧）、`search`（命中 `.hidden` 文件名、不命中正文里的 `needle`）逐项跑过；client 侧另有真 RPC `POST /api/workspaceFiles/list` 200。探针出处：`files.md` 一（F33/F35）、二（原始读回）、三、五，原始记录 `files.jsonl`。

**unknown**：>2000 项的大目录与 2 MiB 分页上限的实际截断行为（只读到契约默认值）；真实 `workspaceChanges.summary` 的返回（需要一次真改文件的回合）。

## 14. `schedule`：每次投递都是一次模型调用

**结论：「提醒」和「定时任务」在宿主眼里是同一件事——投递就是往会话注入一条 prompt，所以一定花 token。** 纯提醒（只弹通知不花钱）只能自建 `ctx.timer` + `storageDomain` + 浮层 toast，代价是重启后要自己恢复计时。

```ts
create({ title, prompt, timing, target })        → ScheduleCatalogEntry
timing = { kind:'after', after_seconds }
       | { kind:'at',    at: { date:'YYYY-MM-DD', time:'HH:mm:ss', time_zone } }
       | { kind:'daily', daily: { time:'HH:mm:ss', time_zone } }
       | { kind:'cron',  cron: { expression:'*/5 * * * *', time_zone } }
       // 另有 every / weekly / rrule：只读到契约，未逐一实建
target = { kind:'session', sessionId } | { kind:'new', create: { cwd } }

list({ active?, limit? })  → { shown, total, limit }
catalog()                  → ScheduleCatalogEntry[]
view({ id })               → ScheduleCatalogEntry
history({ id, limit?, before? }) → { records:[{ scheduledAt, deliveredAt, messageId, targetSessionId, prompt }],
                                     retention: { days: 30, records: 200 } }
edit({ id, action:'update'|'delete', patch? })
deliveryLimits()           → { newSessionIntervalSeconds: 60 }
run({ id })                // = Run now（本轮未实测，会真投递）
```

`ScheduleCatalogEntry` 关键字段：`id / kind / title / prompt / status('active'|'paused'|'ended') / scheduledAt / createdAt / updatedAt / involvedSessionIds[] / lastDelivery{ scheduledAt, deliveredAt, messageId, targetSessionId } / executionActive? / deliveryFloorEndsAt?`。

**注意点**

- **时间格式必须是 `HH:mm:ss`**（可带 1–3 位毫秒）。探针两轮对照很干净：第一轮写 `time:'09:30'` / `'09:00'` 被 `ScheduleInputError` 拒（`Local at requires date YYYY-MM-DD and time HH:mm:ss…`、`daily.time must use HH:mm:ss…`），第二轮补成 `09:30:00` / `09:00:00` 就成功，且回读被规范成 `"09:00:00.000"`。日期同理要 `YYYY-MM-DD`。【实测】
- **到点真的会 fire**：`after_seconds: 4` 的任务 4 s 后 `view()` 变 `status:'ended'` + `lastDelivery{ deliveredAt, messageId, targetSessionId }` + `deliveryFloorEndsAt`，`history()` 里有带 prompt 的投递记录；同期 `api-session/status` 出现 `true → false`、`api-session/error` 报的是模型凭据错误——**这正好证明投递链跑到了模型层**。【实测】
- **`deliveryLimits().newSessionIntervalSeconds = 60`**：`target.kind:'new'` 的投递最少间隔 60 s。想做「每分钟」的任务 = 每分钟一次模型调用，UI 上必须写成本提示。【实测】
- **时区换算是宿主做的**：`{ date:'2026-12-05', time:'09:30:00', time_zone:'Asia/Shanghai' }` → `scheduledAt:'2026-12-05T01:30:00.000Z'`；daily `09:00:00 Asia/Shanghai` → 次日 `01:00:00Z`。【实测】

**验证方式**：临时宿主 + 探针插件 5 轮 boot（write / write2 / write3 / write4 / read），`create`（after / at / daily / cron）+ `catalog/list/view/history/edit/delete` 读回 + `after_seconds:4` 真 fire；环境里 `API_KEY/TOKEN/SECRET/PASSWORD` 全清空，所以「能不能不花 token 就触发」这个判据本身是有意义的。探针出处：`sched.md §0`、`§1`（F30/F36）、`§3`、`§4`、`§5`，原始记录 `sched.jsonl`（`schedule:*`、`2:schedule:create(at|daily|cron)`）。

**unknown**：`run()` 的完整投递结果、`edit` 的 `expectedUpdatedAt` 冲突、`deleteInactive()`、`every/weekly/rrule` 三种 timing——都只读到契约。

## 15. `storageDomain`：跨重启保留的 KV 域

**结论：要一个「重启后还在」的小型状态，用宿主 `storageDomain`，别自己写文件。** 跨 restart 的读写往返已经写验证过。

```ts
DomainSpec = { name, version, layout?, compatibleVersions?, invalidRecords?,
               global?: { schema, initial },
               tables: { [name]: { valueSchema, __key? } } }

open(spec) → Domain {
  name,
  global: { get(), set(value) },
  table(name) → KvTable { get(k), entries(), keys(), size, put(k,v), delete(k), deleteMany(ks), update(k,fn) },
  close(): Promise<void>,
}
```

- 落盘位置：`<DSH_HOME>/storages/<name>.json`（内容 `{ unit:{ name, version }, global, tables }`）。【实测】
- **跨重启保留**：`open` → `global.set({firstRunDone:true,counter:7})` + `table.put('k1')` + `update` → `close()` → **kill 宿主、重启、再 `open`** → 读回 `{firstRunDone:true,counter:7}` 与 `k1` 的 `n:2`，磁盘文件同证。【实测】
- **`name` 一次性占用**：同一进程重复 `open` 同名域报 `already-open`；`open` 另外可能失败成 `backend-not-found` / `facet-unsupported` / `invalid-record` / `version-mismatch`。【静态 + 实测】
- **`valueSchema` / `global.schema` 宿主只调 `.parse()`**：探针用 `{ parse: (v) => v }` 桩就能通过。这是**未公开的内部契约**，升级要复测（同 next-step 的 projection 桩一个套路）。【实测】

**验证方式**：临时宿主 + 探针插件；`storageDomain.open → 读写 → close → 重启宿主 → 再 open` 的真往返，外加磁盘文件内容比对。探针出处：`sched.md §1`（F63）、`§4` 第 3 项、`§5`。

## 17. client 半的三个装配约定：loader `id`、`inputTriggers`、`exports.inject`

1. **`window.__ModuleLoader__.load({ id })` 的 `id` 必须等于包名。** 写错（例如包 `probe-ui`、`id` 写成 `@probe/ui`）会让浏览器报 `client-modules: duplicate factory registration for "@probe/ui"` + `1 entry did not activate: probe-ui: import failed`，**所有 slot 静默不渲染**（面板入口都不出现），而宿主不报致命错误——这是本轮 L5 lane 首轮栽的坑，改成包名后一次通过。【实测】
2. **`@` 提及的注册缝在 client 半的 `ctx.inputTriggers.registerSource(source)`，host 侧没有。** 契约（`dsh-client-ui-input-trigger/src/client/contract.ts`）：`registerSource(src): () => void`（重复 `trigger`/`name` 会抛）、`sessionOf(actx)`；`InputTriggerSource` 形状约 `{ trigger:'@', name, showGroupTitle, candidates(session, { query, quoted, drilled, signal }) → rows[], onPick, lexicon?, matchSpace/matchEnter/matchClaim, header?, openReference? }`。第三方可用性有两个官方包各自证明：`ui-reference`（`inject:['inputTriggers',…]` 注册 file+session 源）与 `ui-skill`（`lib/client.js` 里 `inputTriggers.registerSource(source)`）。**注意别用 host 面判它**：临时宿主 `ctx.get('inputTriggers')` 是 `undefined`，因为它不是 host 服务。【静态】
3. **`exports.inject` 是硬依赖声明**：声明里的服务缺失会让**整个插件不激活**（[rc.2 §6.2](0.2.2-rc.2.md#62-无构建-client-插件可用的界面扩展点2026-11-13-实测) 已记这条），所以要延迟拿的服务用 `ctx.inject([name], cb)` 或 `ctx.get(name)` 判空，不要往 `exports.inject` 里堆。至于「没声明进 `exports.inject` 的服务 `c.get()` 能不能拿到」——本轮**没做独立实验**（`packages/*/lib/client.js` 里 `ctx.get(...)` 到处在用，但那不等于证明了未声明的分支），记为 **unknown**；实践上把用到的都声明、取的时候仍判空。

**验证方式**：真实浏览器 + 临时宿主注册 8 个座位（`ui.md §4` 的清单）；第 2 条只有静态证据（client inspect 三次超时，没能在真浏览器里看到新 `@` 源出现）。探针出处：`ui.md §4`（loader id 坑）、`external.md §4`（F62 / `inputTriggers`）、`external.md §6` 第 10 项（该条的验证状态）；`exports.inject` 的缺服务后果见 [rc.2 §6.2](0.2.2-rc.2.md#62-无构建-client-插件可用的界面扩展点2026-11-13-实测)。

## 18. 调用约定：`signal` 必传、RPC 参数按名包一层

**两条纯「接线」层面的坑，踩了都只报一个泛泛的错。**

1. **插件直调 `state()` / `projections()` 必须传 `AbortSignal`。** 漏了报 `TypeError: Cannot read properties of undefined (reading 'throwIfAborted')`（`projections` 那条是 `reading 'aborted'`）——TS 里 signal 必填、运行时不做兜底。`prompt(...)` 也一样带上。`create({cwd})` 本轮不带 signal 成功过。【实测】
2. **RPC 的 `payload.args` 按「参数名」包一层。** wire 形状是 `{ type:'client-request', rpcId, method:'<namespace>/<method>', payload:{ args } }`（`token → cookie` 后 `POST /api/<namespace>/<method>`）：
   - 单参方法：参数名是 `request` 就 `{ request: { cwd } }`（`session/create`、`session/selectModel`、`session/state`、`session/prompt`…）；
   - **无参方法也要占位**：`{ _request: {} }`（`session/list`），否则 `gateway/arguments-invalid`（错误里会点名缺哪个字段）；
   - `workspaceFiles/list` 这种多参方法直接按名字给：`{ workspaceFileScopeId, path }`；
   - 我们自己的 Remote（`projects/*`）用 `{ name, input }` / `{ id }` / `{ entryId }` 就能直连，不用包 `request`。【实测】

**验证方式**：真 HTTP RPC（与 Web GUI 同一条链路）把 `session/create|list|selectModel|state|prompt(steer)|cancel|rename`、`workspace/archiveSession|unarchiveSession`、`workspaceFiles/list`、`artifacts/list` 各走一遍；`signal` 那条是 round 1 的失败原文与 round 2 的修复对照。探针出处：`session.md §3.1–3.2`、`session.round1.jsonl`（`TypeError` 原文）、`session/rpc.mjs`（wire 形状）、`files.md §5`。

## 19. `compaction` 是部署相关的：CLI 起的 web profile 里没有

**结论：自动压缩不能无条件依赖，插件必须 `ctx.get('compaction')` 判空。**

- **CLI 起 web profile 时被禁用**：`@deepseek-ai/dsh-web-app` 把 `compaction-basic` / `command-compact` / `tool-result-pruner` 全设成 `disabled: true`（`dsh --profile … --dump-config` 可见），因此临时宿主里 `ctx.get('compaction')` 是 **`undefined`**（`compactIfNeeded` / `compactNow` / `compactRegion` / `history` 逐个探测都是 `undefined`）。【实测】

## 21. `gh` 与 `forge`：外部能力的两条边界

**`gh`（本机 2.103.3，keyring 登录）**

- `gh auth status` 的 scopes 是 `gist, read:org, repo, workflow`——**缺 `project`**，所以依赖 project 的子命令（`gh pr create --project` 等）没有权限可用（本轮按红线没实跑那条命令，只读了 scopes）。【实测】
- **`gh pr create` 没有 `--json`**：它只打印 URL（flags 共 20 个）。要结构化结果只能自己 `gh pr view <url> --json …` 或解析 URL。【实测】
- `gh pr checks --json` 字段表：`bucket, completedAt, description, event, link, name, startedAt, state, workflow`；`bucket` 取 `pass` / `fail` / `pending` / `skipping` / `cancel`，**pending 时退出码是 8**（不是 0/1）。【实测】
- `gh api rate_limit`：`core 5000/h`、`graphql 5000/h`、`search 30/min`、`code_search 10/min`。【实测】
- `gh extension list` 为空，`gh webhook` 需要装官方扩展（本轮按红线没装）。【实测】

**`forge`（`@deepseek-ai/dsh-experimental-forge-*`）**

- 它是一整套 GitHub 能力，但**是可选 bundle**：「shipped profiles leave it disabled」，本机 desktop profile 显式列进了 `dsh.profile.bundles`；所以插件里必须把 `ctx.get('forge') === undefined` 当正常分支。【静态 + 实测】
- 有：`repositoryFromRemote` / `changeRequestFromUrl` / `changeRequestUrl` / `findByHead` / `readiness` / `fetchChecks` / **`watch`** / `refresh` / `latest` / `merge` / `markReady` / `rerunChecks` / `requestReviews` / `updateBranch` / `diff` / `compare` / `readReview` / `writeReview` / `submitReview` / `threads` / `viewedFiles` / `commits` / `fileText` / `fileUrl`。**没有 create PR**——官方路径是「给会话发一条用户消息，让模型自己跑 `gh pr create`」。【静态】
- 它占着 `sidebar.session.row.trailing` + `.hover` 画 PR 徽章/悬浮卡（我们若同时画会视觉撞车；slot 是 list kind，能并存）。【静态】
- **起 `gh` 时它会清环境变量**：`scrubbedParentEnv()` + `extendEnv: false`（源码级证据），所以「把 `GH_TOKEN` 存进宿主 `credentials`」对 forge **用不上**；要用自存 token 只能自己解析后直连 API。`readiness()` 就是 `gh auth status --hostname <host>` 的封装。【静态】
- CI / PR 的唯一可用事件源是 `forge.watch(ref, listener)` 轮询（`webhookRuntime` 本部署没装载）：checks 在跑或 `mergeability==='unknown'` 时 30 s、settled 的 open PR 120 s、连续失败指数退避到上限 600 s、merged 停止轮询；同一 forge 同时只有一个在飞的 fetch 会**合批**。所以 30 s 节奏下 graphql 5000/h ≈ 41 个 PR 打满额度。【静态】
- 我们自己的落点：`webServer.register({ kind:'exact', path:'/api/hooks/github', handler })` 写验证通过（能注册、`getOrigin()` 读回），但 `WebRoute` 契约不含任何 cookie / Origin 校验，匿名 POST 是否真能到达**未测到**；本机在本地 ⇒ 默认部署下实际拿不到 GitHub 投递。【实测】

探针出处：`external.md §1`、`§5`、`§6`（写验证清单 1/2/4/7/8）、`§7`、`§8`；`sched.md §1`（F27 的 PR 数据源）另证 `forge.changeRequestFromUrl` / `readiness` 的返回形状。

**unknown**：`findByHead` / `fetchChecks` / `latest` 的真实网络返回（红线：本轮不做 GitHub 写操作、不联网拉 PR）、「prompt 让模型跑 `gh pr create`」的端到端效果（无凭据）。

### 22.4 工具结果进模型的是 `output.render` 产生的 `content`，不是 `value`（2026-11-28 复核宿主源码）

`dsh-tools` 的工具执行结果有两条通道：

- **`value`**：契约注释原文是 “Execution-local canonical value; deliberately omitted from durable events.”
  ——只在执行当次可用，**不进**持久化事件，模型上下文里没有它；
- **`content`**：由 `output.render(args, value)` 产生，宿主用它构造 `tool/result` 消息
  （`createToolResultMessage({ callId, content, isError })`）并持久化，**界面工具卡与模型上下文共用这一份**。

推论（写插件时别搞反）：

1. 想改「模型看到的工具结果文本」，改的是 `render` 的输出；只往 `value` 里加字段**不会**自动出现在模型上下文里
   （除非 `render` 读了它）——反过来，`render` 吐出来的内容模型就一定看得到，UI 工具卡也是同一份。
2. 「把信息藏在 `value` 里就不泄漏给模型」不成立；要控制可见性，得在 `render`（和 value 的构造）上同时收口。
3. advisor 的 U1-11 收敛之所以有效，是因为 `exposeSkip` 把内部开关状态换成中性 reason，而 `renderToolOutput`
   读的正是这份 reason，最终以 `content` 进入模型上下文。

## 23. 2026-11-28 第二轮实测：能力挂载时序、导航、调度契约与命令回执

> 来源：全插件体检与用户模拟后的修复批次（PR #352–#371；各条证据在对应分支的测试/复审与 `docs/testing/*`）。
> 证据等级：**【实测】**＝真机/真宿主或随包源码+真实日志复算；**【静态】**＝只读随包源码/类型声明。

### 23.1 能力挂载时序：`ctx.get()` 启动时可能还拿不到 `workspaceRegistry` / `agents`

- **【实测】**桌面组合启动时，`ctx.get("workspaceRegistry")` 与 `ctx.get("agents")` 在 `sessionPersistence` 可用之后仍可能为 `undefined`，约 1.5s 后才可用（同一进程内 `probeCapabilities` 前后两次日志：`{workspaceRegistry:"undefined", sessions:"object", agents:"undefined"}` → 1.5s 后 `{workspaceRegistry:"object", sessions:"object"}`）。
- **影响**：插件在启动/服务挂载时探测能力并**固化**，会把「暂时没有」当成「宿主不支持」——session-delete 因此跳过归档/停止闸门与工作区记账，删除→恢复链路表现为 `unarchiveSession unavailable`、会话未分组、恢复后 `session/agent-busy`。
- **要求**：能力探测必须**可在操作前重新探测**；服务/门禁集合变化时原地重建引用（不要只缓存一次）。见 `docs/testing/session-delete.md`「宿主事实」与 `packages/session-delete/lib/service.js refreshHost()`。

### 23.2 客户端 `uiWorkspace` 导航（非公开契约）

- **【静态】**`ctx.get("uiWorkspace")` 是 client 服务（`dsh-client-ui-workspace/src/client/navigation.ts`），提供 `openSession(target)` 与 `startSession(workspaceId?)`；`target` 可为会话 id 字符串。
- **用途**：插件在「恢复会话 / 删除当前会话」后把主视图重新绑到会话（session-delete 的「恢复即用」与「删当前会话后切到下一个」）。
- **降级**：缺失时插件应退回「刷新投影 + 刷新列表」，并提示用户手动切换会话；不要把该服务当公开契约（版本升级可能变）。

### 23.3 `@deepseek-ai/dsh-schedule` 的编辑契约

- **【实测】**`schedule.edit` 的 patch 字段是 **`active: boolean`**（`false` 暂停 / `true` 恢复）；**`status` 字段会被静默忽略**（不要让插件照审计建议写 `status`）。
- 返回语义：`create` → task（含 `id`）；`edit` → task / `{ id, deleted: true }` / 抛 `schedule_not_found` / `schedule_conflict`；一次性提醒过期恢复会以 `not_future` 拒绝。
- **影响**：projects 的 pause/resume/delete 对账、`weeklyTokens` 到线自动暂停都依赖它；写错字段会导致「假成功审计 + 定时任务继续跑」。

### 23.4 advisor 命令回执的可用座位

- **【静态】**`conversation.chat.commandview` 是 command 渲染器的 **keyed 子 slot**（key = `command.name`）；宿主通用命令卡片只显示命令名、单行省略号截断，多行输出进第二层折叠。
- **【静态】**`command/executed(sessionId, name, result)` 事件仅在**本地命令执行成功**后由宿主广播；插件可据此渲染自己的命令回执。
- **【静态】**`shell.overlay` 是 root 级常驻槽，**空白会话也渲染**；而空白会话的 command 节点是 log-only（§5.2）——所以「敲完即见」的回执必须用插件自绘的 overlay/面板，不能依赖命令卡片。
- **影响**：advisor 的 `/advisor status|doctor` 回执、btw 的空白会话 `/btw` 回执都采用「自绘 overlay」；`probe:runtime` 已把 `conversation.chat.commandview` 纳入 slot 清单。

### 23.5 `ctx.approval` 在 `approval: never` 下不可用

- **【实测】**本部署默认 `danger-full-access` + `approval: never`：插件裸调 `approval.request` 会在 waterfall 前被短路成 `rejected`（无 open turn 时还会抛错/挂起）。**插件不能靠宿主审批做破坏性操作门禁**（casefile `drop` 因此改为「面板入口 + dry-run + 确认 + 工具描述同意约束」，属文档约束而非强制）。
- 需要硬门时应评估 `tools/pre-execute` seam（本仓库暂未采用，版本风险）。

### 23.6 会话 `surfaceOp` 与冷启动可见性（session-rewind）

- **【实测】**回溯写入的 marker（`user/message` + `source.kind=session-rewind` + `surfaceOp.replace`）在宿主 replay 时是正确的：用真实 v4 日志 + 宿主 `foldSurface()` 复算，模型上下文保持截断；v4 物理格式把 `sourceEventSeqs` 压缩成 `[start,end]` 区间是正常编码。
- **【实测】**客户端必须自己根据宿主 cuts 隐藏被撤回行（replacement marker 不会成为对话节点）；冷启动时 `activeSession` 为 null 会让可见性层拿不到 sessionId，`cuts` RPC 首次失败也会被静默吞掉——两者叠加导致「重启后撤回消息复现」。修法见 `packages/session-rewind/lib/client.js`（动态 sessionId + 退避重试 + 面板补种）。
- 相关：`commandUi.decorate` 的 `ui.kind:"action"` 可用，`/rewind` 用它打开插件自己的候选对话框（取代在空白/长列表下键盘导航不可靠的宿主 `popupSelect`）。

### 23.7 shell 与命令面的边界（补充）

- **【实测】**`ctx.commands`/`commandUi` 只保证「命令注册与装饰」；命令输出在对话流的呈现由宿主 chat 的 command 节点决定，插件无法改变其折叠/截断，只能另开自己的可见通道（§23.4）。
- **【实测】**宿主没有通用 toast/notify 服务；`shell.overlay` 是官方浮层座位（badge/toast/status pill 都放这里）。

### 23.8 插件身份：locale `meta` 经 `exports` 解析，顶层 `icon` 不走 `exports`（2026-11-28 实测）

> 来源：8 个发布插件的「插件身份」修复（U1-01/U1-19，`feat/repo-plugin-identity`）。证据等级：**【实测】**＝用随包源码里真实的宿主函数 `readPluginMeta()` 在隔离 fixture 上调用 + 真机 UI 复验。
> 源码：`app.asar/dsh/node_modules/@deepseek-ai/dsh-app-boot/src/package-meta.ts`（与 `lib/index.js` 一致；`readPluginMeta` 在包根导出，可直接 `import` 调用）。

- **【实测】locale 必须能被 `exports` 解析。** `readPluginMeta(specifier, parentURL)` 用 `optionalResourcePath(`${specifier}/locale/en.json`)` → Node ESM 解析器（`ModuleLoader.fromInternal().resolveSync`）读语言文件；子路径没被 `exports` 声明时抛 `ERR_PACKAGE_PATH_NOT_EXPORTED`，被吞成 `undefined`，标题/描述静默回退 `package.json#name` / `#description`（这就是 U1-01 的「包名 + 英文长描述」）。
  - 逐文件显式（`"./locale/en.json"`）与 `*` 通配（`"./locale/*.json": "./locale/*.json"`）都有效；官方带 `locale/` 目录的包 269/269 全用通配（`dsh-doc/references/host-plugin.md` 推荐的也是通配）。
  - **通配不是「不生效」**：用真实 `readPluginMeta` 对通配包调用，en/zh 字典、title、description、icon 全部正常返回、无 `error`。
- **【实测】`dictionariesOf()` 遍历 locale 目录里的每一个 `.json`。** 它会为目录中每个语言文件再解析一次 `${specifier}/locale/<file>`；**只要有一个文件没被 exports 覆盖**（典型：新增 `locale/ja.json` 但 exports 还只列 en/zh），就抛错让 `readPluginMeta` 只返回 `{ error }`，**title/description/icon 整套丢失**（不是只缺那一种语言）。因此 `exports` 用 `./locale/*.json` 通配最稳；`scripts/check-plugins.mjs` 已加机械检查（locale 目录每个 `.json` 必须被某个 exports 子路径命中、通配目标必须至少匹配 1 个文件）。
- **【实测】顶层 `package.json#icon` 优先且不走 `exports`。** `iconOf()` 在该字段存在时按清单目录解析相对路径，只校验扩展名（svg/png/jpg/jpeg/webp）、必须在包目录内、普通文件、≤256 KiB；只有没有顶层 `icon` 时才尝试 `<specifier>/icon` 导出。所以 8 个包都没有 `./icon` 导出，图标仍以 `data:image/svg+xml;base64,…` 正常返回。
- **【实测】真实宿主函数复核（通配 exports 版本）**：8/8 包返回 `title{en,zh}` / `description{en,zh}` / `icon`，无 `error`；icon data URL 的字节数与 sha256 前缀和真机 UI DOM 证据逐字节一致（advisor 931 B / artifacts 408 B / btw 553 B / casefile 817 B / next-step 589 B / projects 838 B / session-delete 714 B / session-rewind 562 B）。
- **【实测】「发现」页图标来自索引条目的 `icon` 字段**，不读包内 `icon.svg`——「已安装」页读的才是后者（上一节），两条通道互相独立，改一边不会自动同步另一边。
  - 渲染（`dsh-client-ui-plugin-market/src/client/DiscoverSection.tsx` 的 `MarketIcon`）：`icon` 直接进 `<img src>`，`ICON = 36`（36px 图形放在 48px 边框帧里，与「已安装」一致），`loading="lazy"` + `referrerPolicy="no-referrer"`；加载失败静默回退 `PluginArtworkDefault`（通用图形），不报错。**【实测】**隔离实例把索引源指向本地 `build/index.json` 后，8 张卡片的 `<img src>` 与索引 `icon` 逐字节相同且按 36×36 解码（2026-11-28）。
  - schema（`dsh-plugin-market-index/src/index.ts` 的 `icon()` 与 `src/types.ts`）：`icon` 可选；内联形态**只接受 base64 data URL**，MIME 限 `image/svg+xml` / `image/png` / `image/jpeg` / `image/webp`（正则 `DATA_ICON`），**URI 编码的 data URL 会让整份索引被拒收**（`plugin-market/invalid-index`）；内联图标解码后 **≤32 KiB**（`MAX_INLINE_ICON_BYTES = 32 * 1024`）。非 data URL 时按索引 URL 解析，必须解析到 https 或与索引源同源；URL 图标由浏览器代用户请求，会把 IP 暴露给图片主机（README 的 Known Limitations）。
  - **【实测】生成器现在会内联图标**：`scripts/build-index.mjs` 按 `package.json#icon`（默认 `icon.svg`，也支持 png/jpeg/webp 与文件头嗅探）内联成 `data:<mime>;base64,…` 写进条目 `icon`；`--check` 反解后按 sha256 与本地文件逐字节核对，并双向核对索引条目（ghost 插件会报错）。8 个插件源文件合计 **5 412 B**；索引内 data URL 合计 **7 440 B**（base64 载荷 **7 232 B**）；`build/index.json` **15 019 B → 22 539 B**（均含末尾换行），远低于 32 KiB/图 上限。
  - 发现页图标要等 `index.yml` 重建并发布 `@kangyishuai/dsh-plugin-index` 后才在真实用户端出现；发版前可用隔离实例指向本地 `build/index.json` 验证（步骤见 [`docs/testing/index.md`](../testing/index.md) 的「发现页图标」小节）。

### 23.9 宿主 composer 锚点 `[data-composer-input]`（2026-11-28 实测，advisor 定位开始依赖它）

- **【实测】**会话页（空白 hero 态与有消息态都算）的 composer 可编辑元素带 `data-composer-input`：
  `document.querySelector("[data-composer-input]")` 能拿到节点，`getBoundingClientRect()` 返回真实布局
  （1280×820：空白态 top≈411、有会话 top≈700；窗口缩放/多行输入会变）。
- **【实测】**它是**宿主 DOM 锚点**，不是公开服务契约：没有类型声明、版本升级可能改名。生产代码用它时
  必须带 fallback（advisor 的 `toastBottomOffset` 量不到就回退 `bottom:24px`），并在几何变化时重测
  （resize / ResizeObserver / 轮询复核），不能只在挂载时读一次。
- **【实测】**同一锚点在 `shell.overlay` 的跨视图场景里可能暂时消失（切到 projects/casefile 主面板时
  composer 卸载），回到会话后重新出现；依赖它的定位逻辑要能「先回退、之后再跟手」。
- **【实测】卡片锚点与输入框的差值**：同一 composer 的卡片容器带 `data-composer-card`，卡片顶部比
  `[data-composer-input]` 顶部高约 **8px**（卡片的 border/padding，1280×820 实测），与 `.dsh-advisor-toast`
  无关；写几何换算时按「视觉间距 + 8px」折算。
- 用途：advisor 0.6.3 起把回执/轻提示放在 composer 上沿。当前实现
  `bottom = innerHeight - composerTop + 16`（`composerTop` 取 `[data-composer-input]` 顶部；+16 = 视觉
  8px + 卡片 8px），无 composer 回退 24px；真机几何与单测见
  [testing/advisor.md](../testing/advisor.md) 的「回执/轻提示不再遮挡输入区」「复审 N：视觉间距」两节。
