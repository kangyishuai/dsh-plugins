# 0023. next-step：卡片必须落在对话上（修卡调用带对话、空输出重采样、落地校验、无对话不调模型）

- 状态：已接受
- 日期：2026-11-21
- 涉及：`@kangyishuai/dsh-next-step`（v0.4.3）
- 上游：[0009](0009-next-step-architecture.md)、[0013](0013-next-step-gating-telemetry.md)

## 背景

用户报障：卡片**频繁**出现「这一轮没有拿到任何对话内容，上一条回复是空的；因此没有文件名、命令、
diff 或测试结果可以核查……你需要把哪一段对话或哪份改动贴进来？」。这张卡没有信息、没法点击、
每出现一次就是对用户的一次打扰。

第一性原理上看，一张「下一步决策卡」的价值只来自一件事：**它讲的是这段对话里的东西**。
所以先问的不是「模型为什么这样写」，而是「这条路径上有哪个环节允许一张不指向对话的卡片被写进会话」。

排查本机 135 个会话日志（去 fork 重复后约 20 个回合）后，结论是**同一个机制**，而且可以逐字对上：

1. 首次补全的输出**是空字符串**（本机最常见的失败形态）。`parseSuggestion("")` 把它判成
   `json:empty`，`generate()` 于是发起一次「修复」调用。
2. `buildRepairMessage()` 只回贴两样东西：模型上次的原文（空）与「缺少 summary / question」的报错。
   **它不带对话**。模型手里唯一的材料就是「上一次输出为空」这条元信息。
3. 系统提示词第 9 条当初写的是「信息不足时，两个方向应当是『先补信息』与『按现有信息推进』」——
   于是模型忠实地把「补信息」写成了这张卡。
4. 这张卡**结构完全合法**：summary / question 非空、label 2–20 字且不以泛化动词开头。
   校验只检查结构，所以它通过了、被写进会话日志、按档位显示出来。

历史记录里 95 条这样的卡片，每一条都能读出修复调用的原文（「上一次输出为空」「缺少 summary 与
question」「本次请求只包含报错」）——**全部**来自这条路径。会话里那一轮的对话其实一点不少：
被引用的报障回合里，上一条回复有 1393 字正文。

代价是隐性的：`json:empty` 只体现在「修复成功」的静默路径上（修复成功就不写 error 事件），
所以诊断面板上既看不到「空输出有多少」，也看不到「有一类卡是自我指涉的」。

## 可选方案

1. **只改提示词**（去掉第 9 条、加「不许自述生成过程」）：成本最低，但修不了机制——
   修复调用仍然只有「上次输出 + 报错」两样材料，模型仍然必须写点什么。
2. **只做机械过滤**（拉黑 `JSON` / `决策卡` / `贴回` 等字样）：能把这次的症状挡住，
   但拉黑表永远追不上模型的措辞，且会误杀「用户就在讨论这个插件」的正常卡。
3. **让管线具备「落地」这个不变量**（本决定）：谁产出卡片内容，谁就必须看得见对话；
   产出的卡片必须能在这段对话里找到至少一个对象；没有对话就根本不调模型。

## 决定

四条硬规则 + 一条提示词收敛，全部落在纯函数里（`lib/prompt.js`），可单测：

1. **任何要产出卡片内容的调用都必须带同一段对话。** `buildRepairMessage({ transcript, raw, problem })`
   现在把对话原样带进修复请求，并明确「不要描述这次修正本身，也不要要求用户补充对话内容」。
2. **空输出不是格式问题，重发原请求。** `recoveryPlan({ raw })`：`raw` 为空 → `retry`（同一条
   messages 再采样一次）；有内容但格式不对 → `repair`（带对话修格式）。拿空字符串去「修格式」，
   等于让模型凭空造一张卡——这正是事故形态，直接禁掉。
3. **落地校验。** `isGroundedIn(卡片正文, 模型看到的那段对话)`，两条通道命中一条即落地：
   - **具体对象原样出现**（`identityTokens`：版本号/文件名/命令/PR 号/带数字的标识符，或 ≥4 字、
     不像泛化名词的中文片段）；
   - **共享 ≥2 条中文 4 字片段**（`sharedChineseGramCount`）。这条是为了短回答：一句话解释一个概念时，
     卡片通常**改写**答案而不是引用文件名，一个具体对象都没有。2026-11-21 桌面 `--deep` 实测抓到
     这个误杀——卡片共享 12 条 4 字片段、0 个具体对象，被误判「与对话无关」。中文 4-gram 还能穿透
     粘着的动词（「用一句话把二分查找定义为」里含「二分查找」）。

   都不命中则丢弃并记 `ungrounded`。判定用的材料取**未裁剪**的同一窗口（`MATERIAL_CLIP`），
   它不发给模型——摘要里的数字常出现在回答后半段，用裁剪版校验会误杀正常卡。
4. **没有对话就不调模型。** 便宜闸新增 `no-context`（transcript < `MIN_CONTEXT_CHARS` = 40 字），
   强制补生成路径也检查。它不是质量阈值而是**接线检查**：`deriveMessages()` 被宿主改名/为空时，
   让「没接上」在诊断里看起来就是「没接上」，而不是变成一张空卡。
5. **提示词收敛**（`PROMPT_VERSION` 3 → 4）：删掉「先补信息」这条方向；新增「这段对话就是你手上的
   全部材料，它不缺东西」「不要描述你自己这次生成的过程」。提示词管不到的那一半由规则 1–3 兜住。

配套：`generate()` 的结局从 `suggestion | null` 改成显式的 `{ ok: true, recovery }` /
`{ ok: false, failure: "schema" | "ungrounded" }`；新增 error 事件 kind `ungrounded`、
`parse` 取值 `retried`、报表指标 `ungroundedShare` 与对应判读句；设置页诊断的「最近跳过」可以说出
`no-context` / 落地校验；补生成按钮对这两种原因给出各自的文案。

## 影响

- **修掉的是机制，不是措辞**：即使模型再换说法，只要卡片没指向这段对话就落不了地；而修复调用
  现在看得见原料，正常情况根本不会产出自我指涉的内容。
- **代价与口径取舍**（离线用本机 1038 条历史卡片验证，其中 119 条自我指涉）：

  | 口径                                           | 正常卡通过  | 自我指涉卡拦下 |
  | ---------------------------------------------- | ----------- | -------------- |
  | 只看具体对象                                   | 918/919     | 98/119         |
  | 具体对象 **或** 共享 2 条中文 4 字片段（采用） | **919/919** | **98/119**     |
  | 任意中文子串（更宽，未采用）                   | 919/919     | 87/119         |

  4 字片段通道**只赚不亏**：把短回答的改写式卡片救回来，封住自述卡的能力不变。剩余 21 条漏网
  全部出现在「本插件自己的开发会话」里——那段对话天然充满 JSON / 决策卡 / 字段，属已知边界。
  丢一张卡的后果是「这一轮没有卡」，产品判断比一张空卡更差，所以口径整体偏严；放宽成「任意中文子串」
  会多放行 11 张自述卡，故不采用。
- **请求次数不变**：仍然是「首轮 + 至多一次恢复」。空输出时那一次从「修复」改成「重采样」，
  采样成功率明显高于让模型对着空字符串修格式。
- **可观测性**：`ungrounded`、`retried`、`no-context` 三个新标签让这类问题以后**在诊断里就能看见**，
  而不是靠人眼在会话日志里发现一张怪卡。
- **要重新考虑的时机**：若将来 `deriveMessages()` 成为公开 API、或宿主提供「本轮工具输出摘要」，
  落地校验的材料可以扩大到工具结果（现在只用 user / assistant 文本，命令和数字若只出现在工具输出里
  就认不出来）。另外 4 字片段阈值（≥2）是**中文经验值**：若将来主要语言不是中文，这条通道要按语言重设。

## 增补（2026-11-28）：空输出是确定性的，报表口径已经拆开

上线一周后复核本机事件账本（按 `pv` 分段：pv3 = 0.4.0–0.4.2 行为、pv4 = 0.4.3 行为），结论是
`schema` 错误从 pv3 的 19 涨到 pv4 的 102 **不是校验变严**，而是本 ADR 第 2 条规则的统计口径变化：

- pv4 的 102 条 `schema` 里 **79 条（77%）是 `json:empty`**，即模型两次都返回空文本；非空格式失败只有 23 条，
  且 `options` 类（label 超长等）反而从 12 降到 2。校验规则与各上限两版逐字相同。
- **81 次空输出里，把同一个请求原样重发只救回 2 次，79 次仍为空**。若空输出是独立随机（本机估算约 31%），
  重发应能救回约 69%——实际远低于此，说明空输出是「同一请求确定性为空」。
  ⇒ 本 ADR 的「空输出重发原请求」在这种 provider 形态下基本无效；它真正的收益是**不再把空输出写成一张
  自述卡**：0.4.2 走的是「不带对话的修复」，模型只能把「上次输出为空」写成卡，于是同一批回合被记为
  成功并产出了垃圾卡。
- 因此这条路径的代价是「本来会出垃圾卡的回合变成不出卡 + `schema` 计数」，不是「提示词/校验退步」。
  按 `schema` 计数直接下「解析要放宽」的结论会修错地方。

配套的报表改动（`packages/next-step/lib/report.js`，patch）：`summarize()` 把 schema 失败拆成
`errors.byDetail`（`json:empty` / `json:no-object` / `json:unparsable` / `options` 等）、`errors.empty`
与 `errors.format`；`schemaShare` 只算**非空格式失败**，新增 `emptyShare`（空输出占 schema 失败），
`verdicts()` 新增 `empty-generations`（空输出 ≥5 且占 schema ≥50%），文案明确「这是 provider / 输出长度
（`maxTokens`）问题，不是解析要放宽」。事件形状与公开契约不变；读法与阈值见
[docs/testing/next-step.md §7.5](../../docs/testing/next-step.md#75-复盘口径空输出-vs-格式失败2026-11-28-增补)。

残留未知（不影响定性）：空输出率是否也上升了无法干净归因——pv4 窗口被少数几个巨型会话主导，
会话组成/时间与 pv3 不同；空文本的 provider 层成因未查明。若要证实，需要一次受控对比：同一段对话、
同一路由，分别用 v3/v4 提示词各跑，并在临时环境调 `maxTokens` 做只读对照。

## 修订：2026-11-28（空输出预算升级）

规则 2 的「空输出时带上对话原样重发」在推理模型上不足：`zhinao/deepseek-v4.1-flash`（reasoning Max）+ 默认 500 maxTokens 时，推理块会吃掉全部预算（`finish=max-tokens`、`outputTokens=500`、文本为空），原样重发仍为空。修订为：

1. 空输出 → **提高输出预算**（至少 3000，封顶 4000）重发同一个请求；
2. 升级后仍为空 → 带 transcript 要求「只输出 JSON」；
3. 升级后非空但格式错 → 带 transcript + 真实畸形输出修格式；
4. 默认 `maxTokens` 500 → 2000。

「修复请求必须带对话、空字符串不得拿去修格式」这两条不变；`json:empty` 仍作为诊断/报表分桶口径。
