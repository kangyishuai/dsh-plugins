# 0005. 插件与 DSH 版本的兼容与升级策略

- 状态：已接受
- 日期：2026-11-04
- 涉及：repo（所有插件）、session-delete（首个实践者）
- 关联：[ADR 0004](0004-session-delete-architecture.md)、[运行时勘察](../runtime/0.2.1-rc.5.md)

## 背景

DSH 停在 `0.2.1-rc.x` 的预发布阶段，宿主升级频繁；插件是**独立发版的 npm 包**，装在 profile 的 `node_modules` 里（`dsh plugin` 只是把参数转发给 pnpm）。所以 DSH 一升级，宿主包被整包替换，插件代码原地不动——**能力可能悄悄消失，而插件直到被点开才报错**。社区里的典型事故就是这类静默错配（删了一半、界面不刷新、归档幽灵）。

调研中确认了两条关键事实：

1. **DSH 有官方版本闸门**（`@deepseek-ai/dsh-plugin-manager`）：package.json 的 `engines.dsh`（没有则回退到 `@deepseek-ai/*` peerDependencies）不满足宿主版本时，**同时阻止安装与激活**；可用 `allow-version --dsh-version <runtime> --accept-risk` 豁免，但明示「崩溃与数据丢失风险」。
2. **预发布 semver 有个坑**：用宿主自带的 semver 实测（2026-11-04）：

| range                 | 0.2.1-rc.5 | 0.2.1-rc.6 | 0.2.1 | 0.2.2-rc.1 | 0.2.2 | 0.3.0-rc.1 |
| --------------------- | :--------: | :--------: | :---: | :--------: | :---: | :--------: |
| `>=0.2.1-rc.5 <0.3.0` |     ✓      |     ✓      |   ✓   |   **✗**    |   ✓   |     ✗      |
| `>=0.2.1-rc.5 <0.2.2` |     ✓      |     ✓      |   ✓   |     ✗      |   ✗   |     ✗      |
| `^0.2.1-rc.5`         |     ✓      |     ✓      |   ✓   |   **✗**    |   ✓   |     ✗      |

结论：**任何新的 patch tuple 的预发布（如 0.2.2-rc.1）都不满足现有多数 range**。也就是说，
一旦声明了 `engines.dsh`，DSH 每升一个 patch tuple，插件就会被闸门拦在激活之外——
这既是保护（不会带病运行），也是负担（用户必须先拿到我们发的补丁版本）。

## 决定

### 1. 三层防线，按「越晚发现越贵」排列

| 层               | 时机         | 机制                                                              | 失败时的表现                                                           |
| ---------------- | ------------ | ----------------------------------------------------------------- | ---------------------------------------------------------------------- |
| L1 安装/激活闸门 | 插件加载     | `engines.dsh`（**验证通过后才声明**，见 `2）                      | 插件不激活，DSH 明确报版本不满足                                       |
| L2 启动自检      | `apply()` 时 | `capability.js` 探测所有依赖的宿主能力，分级 api/internal/unknown | 进入**只读模式**：plan、审计、回收站列表可用；trash/restore/purge 禁用 |
| L3 执行期拒绝    | 每次操作     | 每个 op 自行校验前置能力；unknown 一律拒绝，绝不半删              | 结构化错误码 + 审计，本地文件零改动                                    |

**L2/L3 是主力。** L1 只在已经验证过两个宿主版本后才开，避免「DSH 一升级插件就消失」的体验。

### 2. `engines.dsh` 的声明规则

- **v0.1 不声明**（与 AGENTS.md「版本约束先留空」一致），靠 L2/L3。
- 当某个插件在**连续两个宿主版本**上通过人工验收后，写入**已验证窗口**，例如 `">=0.2.1-rc.5 <0.2.2"`，并在 README 兼容表加一行。
- 每次 DSH 升级新 patch tuple：发 patch 版本更新窗口（窗口上界随验证结果移动）。
- 不往 range 里塞 `||` 去猜未来版本；猜错等于放行未验证的宿主。

### 3. 版本无关的设计（省钱的最大来源）

- **不解析会话日志**：只用 `stat().header`、目录名、`meta.json`。会话格式 v4→v5 对我们是透明的。
- **路径从 `locate()` 拿**，拿不到才回退「扫描 + 匹配已知布局 + 校验 header.id」，不认识就保留并告警。
- **引用清理优先走 `workspaceRegistry` 公开方法**（archive/unarchive/pin/unpin/detach），文件级兜底只在 internal 档使用。

### 4. 升级前后的固定动作

**我们（维护者）**：

1. 升级前：`node scripts/probe-runtime.mjs`——解析 `app.asar`，逐项核对插件依赖的 API 面（方法是否存在、slot 名是否还在 client bundle 里），输出 diff。
2. 升级后：新建 `docs/runtime/<新版本>.md`，逐项勾选；跑一遍 GUI 手测清单（删除/恢复/彻底删除/改到一半断电）。
3. 发版：`pnpm changeset` → patch（兼容修复）/ minor（0.x 破坏性变更）→ README 兼容表更新。

**用户**：

```
1. 升级 DSH → 重启
2. 打开 设置 → 插件 → session-delete，看状态条：
   - 「就绪」→ 正常用
   - 「只读模式（宿主版本未验证）」→ 只能查看与导出，破坏性操作已禁用
3. 升级插件：dsh plugin --profile desktop add @kangyishuai/dsh-session-delete
   （或直接在插件市场里点更新）
```

### 5. 禁止静默失败

- client 半启动时做一次自检（slot 是否注册成功、remote 是否可取），把结果通过 host 的 `health` 方法上报，写审计；
- 降级状态必须**在界面上可见**（回收站面板顶部横幅 + 菜单项 tooltip），不能只写日志；
- 任何拒绝都要带结构化 `code` 与人类可读原因，客户端原样展示。

### 6. 数据格式与回滚

- `meta.json` 带 `schemaVersion`；新版本读旧条目、旧版本忽略新字段。
- **卸载插件不删回收站**（那是用户的恢复通道）；README 写明路径。
- 回滚 = `add <pkg>@<旧版本>`；因为 trash 格式向后兼容，回滚后仍能恢复旧条目。
- 若被 L1 闸门拦住而用户确认要用，可以提供 `allow-version` 命令，但必须在 README 标注「未验证，风险自负」，不作为推荐路径。

### 7. 症状 → 处理对照表（写给用户，也给我们排障）

| 症状                       | 大概率原因                                        | 处理                                      |
| -------------------------- | ------------------------------------------------- | ----------------------------------------- |
| 侧栏菜单里没有「删除会话」 | 插件的 client bundle 未加载（slot 改名/包未激活） | 看插件状态条 health；确认插件已启用       |
| 菜单在，点了报「只读模式」 | L2 探测到宿主能力缺失（新版 API 变了）            | 升级插件；报 issue 附 health 输出         |
| 删除成功但行不消失         | client 的移除事件通道变了                         | 刷新页面；报 issue（附宿主版本）          |
| 恢复后归档标记丢了         | 归档集合接口变更                                  | 该条仍可在回收站重试；报 issue            |
| 彻底删除只删了一半         | 触发了 unknown 档却没拒绝 → **bug**               | 用回执与审计定位；该记录进 journal 可续做 |

## 影响

- 多写约 120 行探测与降级代码，换「升级不炸、炸了能看出来」。
- DSH 升级不会让插件静默带病运行；代价是可能进入只读模式，需要等我们发补丁。
- 维护成本：每个 DSH 版本一份 runtime 记录 + 一次探针 diff + 一次手测。
