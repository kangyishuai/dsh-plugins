# ADR 0009：next-step —— 一个包两个面，状态属于会话数据

- 状态：已接受
- 日期：2026-11-10

## 背景

目标是在 DSH 里做两件相关的事：

- **A｜决策卡**：一轮回答正常结束后，在回答下方给一张卡片——一段现状摘要、一句提问、两条方向互斥的建议；点任意一条，就把该条文本当作**用户消息**发出。
- **B｜幽灵提示**：输入框为空时，框内给一条灰色下一条 prompt 建议；`Tab`/`→` 接受成可编辑文本，`Enter` 才发送。

生态调研（2026-11-09/10，90 个同区域项目 + 5 个 A 类实现）显示：B 已经饱和（15 个实现、头部 30 天 3.5k 下载），A 有 5 个实现但都缺「摘要 + 提问 + 恰好两条互斥动作 + 严格门控」的组合；宿主还有 opt-in 的 `dsh-action-cards`（主模型通过 `propose_action` 工具出卡，卡片动词不是发文本）。

另一个关键事实：用户提供的参照实现（Claude 桌面版）里，点击按钮后**卡片还在、按钮消失、点击文本变成一条右侧用户消息**，往上滚还能看到更早的卡片——说明卡片状态属于**会话数据**，不是界面层的浮层。

## 决策

1. **一个包，两个可独立开关的面。** `card`（默认开）与 `ghost`（默认关）共用一个包 `@kangyishuai/dsh-next-step`，共享触发点、一次模型调用、设置与预算。理由：两者的触发时刻相同（轮末）、产物同源（同一次补全）、必须互斥（卡在时不显示幽灵）；拆两个包会重复一遍触发/调用/开关，并把「互斥」变成跨插件协调，且仓库硬性要求每个带 client 半的包各有一份桌面冒烟。
2. **一次调用产出三个结果。** 同一次补全返回 `{summary, question, options[2], nextPrompt}`：卡片用前三个，幽灵提示用最后一个。相邻生态的成熟做法（Open WebUI 把 `followUps[0]` 直接当输入框灰字候选）证明这样省一半 token。
3. **状态属于会话数据：插件记录 + 会话投影。** 卡片与决策分别用 `appendPluginRecord(session, "plugin:next-step/card" | "plugin:next-step/decision", data)` 写进会话日志；host 半注册 `ctx.sessionProjections.register({key:"nextStep", …})`，客户端用 `useProjection("nextStep")` 读。刷新、切会话、fork 之后状态都还在；「点击后卡片保留、按钮消失」不再是界面技巧，而是记录了 `phase: "sent"` 的自然结果。
4. **状态是对话的一部分；卡片本体贴在输入框上方。** 卡片渲染在 `conversation.input.overlay`（composer 卡片内的覆盖层锚点），因此它**始终在视口里**——不用为了看建议去滚动，也不会盖住输入框；代价是它视觉上属于输入区（在 composer 卡片内部顶部），而不是像 Claude 那样排在 transcript 里。
   最初的设计是渲染在 `conversation.chat.turnTail`（答后 footer，官方 action-cards 用的位置），实测发现：卡片虽然位置「正确」，但答完时视图停在答案底部，出现在更上方的卡片经常在视口之外，用户根本看不到；因此改为 composer 覆盖层，并在 README 与 §2.5 里如实写明这个取舍。
   无论渲染在哪，**状态都属于会话数据**：历史轮次的卡片保留但只读，任何时刻最多一张可交互卡（只对最后一轮渲染胶囊），复刻 Claude 的「点过之后只留记录」。

5. **点击 = 用户消息，走宿主输入框。** `setDraft(text)` → 轮询等编辑器草稿落定 → `submit()`（内部 `mode: "queue"`，与手动回车同一条提交链）。不伪造会话事件。发送前的决策记录让界面立即进入只读态；草稿非空时禁用胶囊（`setDraft` 是整篇替换，会覆盖用户正在打的字）。
6. **严格门控。** 只在 `turn/end` 且 `reason.kind === "completed"` 时生成；Stop/报错/`max-tokens`/待审批一律不出卡；子代理会话不出卡；流式期间宿主本来就不渲染 turnTail 节点。官方 action-cards 只判「有没有最终文本」，会在 `max-tokens` 后误出卡——这里做对，是产品可信度上的差异点。
7. **开关 = 不再发请求，而不是隐藏 UI。** 设置在 `$DSH_HOME/next-step.settings.json`，host 每次生成前重读（1s 缓存），所以改文件即生效、不需要重启；`enabled=false` 时在发请求之前就返回。另有 `pauseUntil`、`maxCardsPerSession` 预算闸与超时（默认 20s）、失败静默。
    > 2026-11-14 补注：**超时与取消**这两个中止原因不再完全静默——它们会计入 `aborted`、写进诊断的「最近跳过」，补生成按钮也会显示「生成超时或被取消」。这不违背「失败静默」的本意（仍然不出卡、不弹框、不把回合弄坏），而是补上可诊断性：此前中止既不计数也不落日志，一次「没出卡」事后完全无法定位。
8. **幽灵提示默认关。** 它必须 portal 进编辑器位置盒、复用宿主 placeholder 的 class 才能保证同基线同字号——这是私有 DOM 依赖，宿主升级会静默失效。把它做成默认关闭的 flag，失败时只是没有提示。

## 备选方案

- **两个包**：见决策 1。除非 B 要单独面向市场（它已饱和），否则不值得。
- **纯客户端状态**：实现最简单，但刷新即失忆，且「点击后卡片还在」只能维持到下一次重渲染，直接违背用户要的持久效果。
- **让主模型调工具出卡（官方 `propose_action` 路线）**：零额外请求是优点，但依赖主模型配合，模型不调就没有卡；且卡片动词语义与「点一条=发一句话」不同。保留为后续可选项（可复用官方卡基建），不在 v1。
- **主模型直接沿用官方投影**：`dsh-action-cards` 只在 opt-in bundle 里，不能假定启用；插件自带一套投影更可控。

## 后果

- 好：状态可审计（谁在什么上下文下被建议了什么、选了哪条），可随会话 fork；客户端不需要轮询或内存态；两个面对外的成本与开关只有一个入口。
- 代价：
  - 依赖三条私有 seam：`conversation.chat.turnTail`、`ctx.sessionProjections.register`、composer facade 的 `setDraft`/`submit`（外加幽灵提示的 `conversation.input.overlay` + placeholder DOM）。升级 DSH 可能静默失效；`pnpm probe:runtime` 需要跟进体检项。
  - 每次触发多一次真实模型调用，占用用户额度；`max-tokens`、限流、超时都必须静默降级（超时/取消只在诊断与补生成按钮上留痕，见第 7 条的补注）。
  - 插件记录会随会话增长（每轮最多一条），`maxCardsPerSession` 只限制生成数量。

## 验证

见 [docs/testing/next-step.md](../../docs/testing/next-step.md)：单测（提示词/解析/设置）+ web 冒烟（临时 `DSH_HOME`、真实宿主）+ 桌面 CDP 只读冒烟（硬性要求）。

## 增补（2026-11-11）：v0.2 的四个取舍

**1. 按钮文本 = 发出去的用户消息（WYSIWYG）。** v1 里胶囊显示 20 字短标签、实际发送背后 240 字的 `text`。实现后暴露两个问题：用户点的是 A、transcript 里却是另一段话（不可预期、不可审计），而「点后回显按钮文本」的需求会把这个错位藏起来。v0.2 起：`options[].label` 就是点击后原样发送的消息，限制从 20 放宽到 4–60 字（可说两行），`text` 字段移除；旧记录里残留的 `text` 被忽略。代价是指令自足性下降，用提示词约束（动词开头、单独发出去就能干活）补足。

**2. 判断权交给模型：`needed` + `reason`。** 「是不是该出卡」没有可靠的启发式；Claude Code 的 `AskUserQuestion`（只在被卡住时才调用）与 DSH 原生 `ask_user_question` / 官方 action-cards 都把判断权放在模型侧。v0.2 沿用同一次额外调用，但输出里加 `needed: boolean` 与 `reason`：`needed=false` 时不写卡、把理由记进 `lastSkip` 并在设置诊断里显示。代价：这次调用仍然发生，省的是界面噪音而不是 token；换来的是「没出卡」有字可查，而不是静默。

**3. 「没出卡」必须有出口：手动补生成。** 光有 `reason` 只能解释，不能补救。v0.2 在最新一轮没出卡时于回答下方渲染一行「生成下一步建议」，走新的 `nextStep/generateNow` Remote 强制生成（无视 `needed`，但仍受总开关与预算约束）。这样「我觉得该出卡却没出」可以一键变成可复现的验证，而不是只能猜是 BUG 还是模型判断。

**4. `⌘↵` 只在安全窗口里接管。** 该组合是宿主 composer 的「Queue/Steer 互补发送」（`fixed.complementary`），直接抢占会破坏排队语义。但宿主源码写明空草稿时它是 empty-draft no-op（`dsh-client-ui-conversation`）。因此 v0.2 通过 `shortcuts.observeFixedInput` 旁听，只在「输入框干净（无草稿/附件/引用/声明，菜单未开）+ 会话空闲 + 本会话有可交互卡」时 `consume()` 并触发 primary，其余情况完全透传。键帽不再是装饰，但也不是全局快捷键。

**勘误：卡片一直渲染在 `conversation.chat.turnTail`。** 上面的决策 4 与旧版 README 写的「改为 composer 覆盖层」与代码不符（截图也显示卡片在回答下方、action row 上方）。实际实现（v0.1.0 起）注册在 `conversation.chat.turnTail`；ADR 保留原文以保留决策历史，以此处为准。

## 增补（2026-11-14）：v0.3.0 把内容质量变成机械校验

v0.2 的 `label` 上限是 4–60 字，实测退化成「检查定义是否准确」这类**放到哪一轮都成立**的按钮：
相关性说得过去，但点不动。对照 Claude 桌面端的建议卡，它的胶囊都是「动词 + 具体对象」
（`改成 %5`、`写 v1.3`、`出 v1.5 和 E2E-01c`，多为 4–13 字）。

v0.3.0 的取舍：

1. **`label` 收紧到 2–20 字，并要求含具体对象**。具体性不只写在提示词里——
   `concreteTokens()` 抽文件/路径/命令/版本号/中文名词片段，`isGenericLabel()` 判定
   「空话动词 + 无具体对象」的按钮并丢弃；一条都不剩时整卡不出（宁可不出，也不出套话）。
   这推翻上文「从 20 放宽到 4–60 字」的结论：放宽的代价是按钮变成一整句话，实测点击意愿更低。
2. **`options` 从「恰好 2 条」改为 1–2 条**：下一步很明确时只给一条，不再凑第二个方向；
   两件事都要做时合并成一条 label（「两件都办」）。
3. **摘要禁止旁白**：要求写可核查事实（文件名、命令、数值、测试结果），
   不接受「用户要求……助手已经……」这种复述。
4. **多两道便宜闸**（`lib/gates.js`）：上一轮不是 `completed` 不出卡；回答短于 80 字不出卡。
   前者避免在错误旁边推销下一步，后者是因为没有上下文时生成结果必然是套话。
5. **幽灵提示与胶囊是同一个建议的两种入口**：`nextPrompt` 上限 150 字（关键信息前 60 字），
   并与推荐胶囊共享至少一个具体对象；不一致时退化成该胶囊文案，而不是各说一件事。

**设置渐进披露。** 总开关关闭 = 不发请求，所以卡片/幽灵/暂停/预算/诊断整段不渲染，只留开关与一行说明；重新启用时子开关取值保留。

## 增补（2026-11-14）：v0.4 把「该不该出」与「要不要显示」拆开

v0.2 的 `needed` boolean 与 v0.3 的严格解析都被实测证明会**单向欠出卡**，而且三种「没出卡」的结局
（模型判 false / 便宜闸拦下 / 解析丢弃）全部无痕。v0.4 的处置——三档判定 + 用户可选档位、
候选与显示解耦 + 揭示、`<dataRoot>/next-step/events.jsonl` 逐轮采集、Wilson 区间的复盘报告——
连同被否决的方案写在 [ADR 0013](0013-next-step-gating-telemetry.md)。本 ADR 的其余决策不变。
