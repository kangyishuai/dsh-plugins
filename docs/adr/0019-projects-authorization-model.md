# 0019. projects：危险动作可配置，但授权来源不可伪造

- 状态：已接受
- 日期：2026-11-17
- 涉及：projects

## 背景

`projects` 会自动执行一些有副作用的事（归档线程、回收 worktree、合并 PR、清理分支）。
最初的草案把这些写成「永久禁止」，但这条线画得太粗：

- **永久禁止会把能力做死**：用户在自己的仓库里完全可以接受某些自动动作；
- **完全交给模型判断则是失控**：模型、外部评论、其它 agent 的输出都可能夹带"去合并吧"，
  把它们当成授权等于把执行权交给不可信输入。

真正需要固定的不是「哪些动作能做」，而是「**授权从哪来**」。这也是与 Claude 侧
「PR 已批准 / 已排入合并队列」等机制对齐的地方——那些机制的授权来源仍然是人的 approve。

## 可选方案

1. **硬白名单**：一组动作永远禁止。缺点是把产品做成死物，且"禁止"无法随用户信任变化。
2. **模型自主**：模型决定就执行。缺点是把不可信输入抬成授权来源，事故不可追。
3. **动作可配置 + 授权来源固定**：动作由用户开关决定能不能自动跑，授权只允许来自三处且不可伪造。

## 决定

选 **3**。

### 授权来源只有三处（按动作固定，不可由配置改变）

| 来源             | 含义                                        |
| ---------------- | ------------------------------------------- |
| `policy-grant`   | 项目设置里一次授予，随时可收回              |
| `approval-event` | 外部系统产生的人类批准（如 GitHub approve） |
| `per-incident`   | 每次都要人点一次                            |

**模型输出、外部内容（PR 评论 / 网页 / 文件）、其它 agent 的消息永不构成授权。**
实现上由 `lib/untrusted.js` 的 `classifyTrust()` 与 `isAuthorizing()` 落地：只有
`trust: principal` 的内容可以授权，其余一律按数据包装（`wrapUntrusted`）。

### 六个开关，默认全 off（「归档」是唯一默认 on 的自动化动作）

`forcePushOwnBranch` / `pushProtectedBranch` / `autoMerge` / `trashAuto` /
`purgeAfterRetention` / `editProfile`。

### 每条动作都带不可配置的硬前提

归属核查、ruleset 探测、CI 与 approve、diff 阈值、可恢复清单——开关打开不等于放行，
只是"不再被默认拒绝"。动作与开关是**显式映射**（`lib/executor.js` 的 `switchForAction()`），
不存在"打开别的开关就能执行"。

### 四条元规则（任何自治级别、任何开关都改不了）

1. 授权不可伪造；
2. 不可逆动作必须留恢复证据（旧 SHA / 回收站 / 清单 / 审计，缺一不执行）；
3. 不得自我提权（不能改自己的审批、预算、审计开关）；
4. 凭据不进模型上下文（需要鉴权的由宿主执行，模型只传句柄）。

### 结构性硬边：这几件事**不提供**该能力

不是"默认关"，而是根本没有实现路径（见 ADR 0021 与 README 的「不支持」清单）。

## 影响

- 危险动作**不是**协调器工具：协调器只能 `project_request_action` 进审批队列；
  **批准 ≠ 可执行**（还要开关打开 + 影响面在阈值内）。
- 自治级别（L0–L3）只影响"提议还是直接干"，**永不改变六个开关的默认值**。
- 拒绝不是错误：返回 `executed: false` + 原因，并写审计。
- 增加新动作时必须同时补：开关映射、硬前提、恢复证据、审计字段、单测与真机断言。
