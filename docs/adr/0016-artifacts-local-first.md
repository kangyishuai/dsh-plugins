# 0016. artifacts 的产品形态：本地优先，发布目标可插拔

- 状态：已接受
- 日期：2026-11-16
- 涉及：artifacts

## 背景

Claude 的 Artifacts 有两个层次：claude.ai 的内容套件（模板、协作、评论）与 Claude Code 的「把会话产出发布成云端网页」（`Artifact` 工具族 + `claude.ai/code/artifact/<id>` + 版本 + 共享 + 评论 + connector 实时数据）。后者是**服务端产品**：托管、账号、组织权限、评论订阅、审计合规都在 Anthropic 侧。

DSH 侧的现实：宿主没有 artifact 存储、没有账号体系、没有分享后端；`ctx.webServer` 只服务本机 GUI，`--host` 属于 web profile 且暴露整站。插件能提供的是「本地渲染 + 本地路由 + 本地版本」，不能提供「云端托管 + 组织权限 + 协作」。

调研证据与逐项差距见私有笔记 `notes/artifacts/`（`dsh-feasibility.md`、`replication-gaps-and-differentiation.md`）。

## 可选方案

1. **复刻云端形态**：插件内起一个可对外托管的服务，模拟 URL/共享/评论。
   - 优点：最接近 Claude 的体验。
   - 缺点：需要用户自建服务与身份、要处理公开链接的安全与合规、与 DSH「本地优先、零账号」的定位冲突；社区唯一真发布实现 `dsh-gh-pages-artifacts` 借位 GitHub Pages，仍是 0 star。
2. **只做本地渲染与预览**（右栏 iframe、库、封面）。
   - 优点：成本最低、零风险。
   - 缺点：产物仍散在文件系统，没有"交付物"这一层。
3. **本地优先 + 可插拔发布目标**：核心是本地工件库（存储/版本/面板/封面/只读 URL），发布只作为"可选出口"（导出单文件、用户自备静态托管、反代）。
   - 优点：拿到 90% 的本地价值、零后端；给未来留出口。
   - 缺点：没有"发链接给别人"的默认能力。

## 决定

选 **方案 3**。v0.1 只交付本地部分；`/artifacts/<id>` 是给本机浏览器看的只读 URL，不承诺跨机器可达。分享相关（加密单文件、自备托管）在路线图里，且必须先有设计稿（见私有笔记 `encrypted-share-design.md`）。

**明确不做**：云端托管、账号/组织权限、评论线程、实时协作、审计合规。

## 影响

- 插件不新增任何需要安全审批的托管域名——这正是企业场景能过审的形态。
- README 必须写清「工件 URL 不是访问控制边界」；局域网/公网只给三条自担风险的路径。
- 若未来要做分享，先加设计（威胁模型 + 密码学参数 + 失败文案），不要顺手加一个"上传到某处"的开关。
- 若官方宿主将来提供 artifact 服务，应重新评估：本 ADR 的"发布目标可插拔"预留了适配器位置（导出器接口），不需要推翻数据模型。
