# 0021. projects：auto-fix 的边界（修代码可以，改测试不行）

- 状态：已接受
- 日期：2026-11-17
- 涉及：projects

## 背景

`projects` 可以观察线程的 CI 结果，在失败后自动再修一轮。这条能力最容易失控：
让"自动修 CI"变成"自动把测试改绿"，等于用自动化掩盖真实缺陷。

## 可选方案

1. **允许改测试**：能更快变绿。缺点是它可以自我认证——测试失去意义。
2. **只允许改实现**：失败要么真被修好，要么停下来等人。缺点是有些失败确实是测试写错。
3. **禁止 auto-fix**：安全但把这个功能的价值归零。

## 决定

选 **2**，并把边界写进代码而不是文档：

- `lib/autofix.js` 的 `touchedTestFiles()` 检查本轮改动是否碰到测试文件
  （`.test/.spec.[cm]?[jt]sx?`）；一旦碰到就**停下**，转人工；
- `MAX_FIX_ROUNDS = 3`：轮数上限，避免无限烧 token；
- `errorSignature()` 抹掉时间戳/耗时/行号/sha：同一错误重复两次仍未修好就停（避免无效重试）；
- 无进展（diff 与上轮相同）也停；
- 判定顺序固定为：**碰到测试 → 同一错误两次 → 无进展**，任何一个命中即停。

auto-fix 不做的事：不 push、不开 PR、不改 CI 配置、不跳过检查、不动审批与预算。

## 影响

- 有些"测试本身写错"的失败会停下来等人——这是**刻意的**，代价换来"测试仍是独立的裁判"。
- 每轮都会写审计（`autofix/*`），包含签名、轮数、停止原因、触发的测试文件。
- 若要放宽（比如允许在明确标记 `@autofix-may-edit` 的测试里改），必须新开 ADR 并同步更新
  `touchedTestFiles()` 的判定与单测。
