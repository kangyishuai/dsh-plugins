# 0013. next-step：三档判定、展示与生成解耦、本地事件与复盘闭环

- 状态：已接受
- 日期：2026-11-14
- 涉及：`@kangyishuai/dsh-next-step`（v0.4.0）
- 上游：[0009](0009-next-step-architecture.md)（一个包两个面，状态属于会话数据）

## 背景

v0.2 起，「这一轮要不要出卡」由模型在**同一次额外调用**里自评一个 boolean（`needed`）。
实测下来这条判据不可靠，而且是**单向**不可靠：模型为了避免出废话，倾向判 `false`，
于是「必要的时候也不出卡」。

更麻烦的是**不可观测**：判 `false`、被便宜闸拦下、解析失败——三种结局都没有留下任何记录
（只有内存里的 `lastSkip`，下一次生成就被覆盖）。卡片记录只覆盖「出了卡 → 点了 / 关了」，
而我们要优化的恰恰是「该出却没出」。没有分母，没有对照，放宽门控之后也无从判断是否过头。

同时代码里有三处**确定性的**丢失（与数据无关，读代码即可确认）：

1. 会话预算 `maxCardsPerSession = 30` 命中后静默不出卡，界面无任何提示；
2. 短答闸看「最后一条回答 < 80 字」，工具密集型回合的收尾回答常常只有一句（「改好了」），
   上下文充分却被判「没有上下文」；
3. 解析是**全有或全无**：label 超过 20 字、summary 超过 400 字、question 超过 200 字、
   reason 超过 160 字、或所有 label 都被判空话 → `parseSuggestion()` 返回 `null`，
   整张卡丢弃，且没有重试。模型输出长度天然有方差，于是格式问题由用户承担损失。

## 可选方案

1. **继续调 boolean 的阈值 / 换更强的模型**：不解决问题——判据本身把「确定没必要」和
   「说不准」压进同一个 `false`，且仍然不可观测。
2. **每轮都出卡**：模型调用本来就每轮发生（`needed=false` 也照调），所以放宽只增加 UI 噪音、
   不增加 token。但「每轮都出」等于放弃判断，与「不是每次必出」的产品要求冲突。
3. **三档判定 + 用户可选档位 + 全量留痕**（本决定）：把「该不该出」与「要不要显示」拆开，
   由档位决定显示阈值；每个合格回合都落一条事件，无论出没出卡。

## 决定

**1. 判定语言从 boolean 改成三档**：`value: "must" | "could" | "no"`。提示词里明写
「**拿不准一律判 `could`，判 `no` 必须能说清为什么继续是负价值**」。boolean 之所以欠出卡，
就是因为它把「确定没必要」和「说不准」混成一个 `false`。

**2. 展示阈值与生成解耦，档位由用户选。**

| 档位           | `shown = true` 的条件                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 严格           | `must`                                                                                                                             |
| 平衡（默认）   | `must` + `could`                                                                                                                   |
| 积极（实验档） | 三档全出（含 `no`）——故意偏离 [plugin-conventions §7.6](../../docs/plugin-conventions.md) 的「只在有真决策时出卡」，仅用于校准判断 |

`shown` 在**写卡时冻结**（不随后续改档位回溯历史）。**候选落库与档位无关**：只要模型调用成功
就写一条卡片记录（`shown` 只是要不要现在显示的标记），否则被抑制的回合根本没有内容可以补。

**3. 没出卡也留候选 + 即时揭示。** 客户端照旧渲染「生成下一步建议」按钮；点击后优先**揭示已有候选**
（新增 `plugin:next-step/reveal` 记录 + 投影 `reveals`），**不发模型调用、瞬时出卡**。
只有这一轮压根没生成过候选时才真的再调一次模型。收益：补卡不再等 20 秒、不重复花钱；
「用户点了揭示」是「模型判 `no` 但用户想要」的最强证据。

**4. 逐轮分析数据落 `<dataRoot>/next-step/events.jsonl`，不进会话日志。** 事件类型：
`meta` / `turn` / `action` / `followup` / `impression` / `promote` / `error`。沿用 advisor 的
`decisions.jsonl` 约定（一轮一行、append-only、2 MB 滚动保留一份历史）。会话日志只放
「卡片候选」与「用户决策」（它们是会话的一部分，要能 fork / 刷新 / 揭示）。

**5. 三个口径必须写死，否则复盘会自欺：**

- **「忽略」用左连接算，不写状态机**：`action` 只在真动作时写，报表把 `shown` 的回合与 `action`
  左连接，其余计入忽略。早先设想的「等下一个事件时仍无动作就写 ignored」在用户关窗/切走/再也不回来时
  永远不会写出——而那恰恰是分母里最重要的一类。
- **曝光必须有可见性证据**：客户端用 `IntersectionObserver`（相交比 ≥0.5 且持续 ≥300 ms）上报
  `visibleMs` 与 `ratio`；宿主按 `sid+turn` 去重。只记「组件挂载」会让曝光率永远接近 100%，
  「没看见」和「看见但不要」就永远分不开。无该 API 时记 `ratio: -1`，报表单列「未知」，不进分母。
- **不写用户原文**：只留长度、延迟、与胶囊重合的具体对象个数（用现成的 `concreteTokens()`）。
  胶囊文案（我们自己生成的 ≤20 字 × 1–2 条）要写，因为复盘按钮文案必须看它；摘要/提问只写长度。

**6. 宽容解析 + 一次修复调用。** 展示文本超长截断；单条 option 不合格只丢这一条；
结构坏/缺值/一条可用建议都不剩时，把「原文 + 具体问题」再发一次，只要求修格式（最多 1 次）。
`needed` 旧字段仍做兼容映射（`true → must`、`false → no`），避免提示词漂移让整张卡作废。

**7. 修掉三处确定性丢失。** 预算默认 30 → 120 且**只统计出过的卡**（它是界面噪音阀门，
不是生成次数阀门）；短答闸改为「本轮回答总字数 < 80 **且** 本轮无工具调用」；被档位抑制的候选
不占预算。

**8. 复盘是人工闭环，不做自动调参。** `nextStep/report` 读事件 → 指标（比例给 Wilson 95% 区间）→
判读句 → 一份 Markdown（保留最新 20 份）。样本门禁：`turns < 80` 或 `shown < 25` 时**只列计数、
不给任何判读**。每次改提示词或按钮规则就 `PROMPT_VERSION + 1`，报表按版本分组对比——没有版本位
就等于没有数据。

## 影响

- **数据是本地文件**，装机即开始写 `events.jsonl`（`telemetry: true` 默认开，设置里可关）；
  2 MB 滚动、设置页显示体积。不联网、不上传。
- **会话日志每轮多一条卡片记录**（只含生成成功的回合，≤1 KB）。旧记录缺新字段时按
  `shown: true / value: "must"` 读——v0.2/v0.3 的卡都是「模型判定需要」才写的。
- **设置文件升级到 v2**，含 `schemaVersion`。v1 → v2 迁移只做一件事：`maxCardsPerSession`
  **恰好等于旧默认 30** 时抬到 120；显式写过 `schemaVersion: 2` 的文件即使值是 30 也不动。
- **设置页按 [plugin-conventions §7.2](../../docs/plugin-conventions.md) 收敛**：首屏 3 行
  （启用 / 出卡频率 / 决策卡）+「更多设置」折叠（幽灵、采集、暂停、预算、诊断、回顾）。
- 新增两个私有 seam 使用点（都不新）：`session/event` 的 `user/message`（followup 归因）与
  `IntersectionObserver`（客户端，非宿主 API）。
- **以后要重新考虑的情形**：若事件样本积累后 `must` 与 `could` 的点击率区间始终重叠，
  说明三档没有区分力——那时应当改提示词的判据描述或退回两档，而不是继续加档。
